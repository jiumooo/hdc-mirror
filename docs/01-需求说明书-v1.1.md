## 1. 硬约束（不可协商的技术边界）

这些不是设计选择，是已核实的物理/授权边界。任何功能设计必须在此约束内成立。

| ID | 约束 | 依据 |
|---|---|---|
| **C1** | 手机零安装 ⇒ 屏幕采集**只能**复用华为 `libscreen_casting.z.so`，由 PC 端推送到 `/data/local/tmp` 后用 `hdc shell uitest start-daemon` 拉起 | 自研采集必须写 HAP 装机；且设备侧 XPM 有签名校验，自研 `.so` 塞进去加载不了 |
| **C2** | 「手机控制中心可选输出对象 + 选中电脑后手机静音」**只能**用蓝牙 A2DP Sink 实现 | 内录只是复制音频，不注册成系统音频设备，手机照常外放；第三方无法改系统音频路由 |
| **C3** | `hdc` 是 PC ↔ 手机的唯一通道（无线调试 / TCP） | 用户要求手机零安装 |
| **C4** | 不做代码签名 | 用户明确「签名无所谓，只要用户放行安装就行」 |
| **C5** | 上游那套 `hosScrcpy-*.jar` 自包含 grpc/netty/protobuf，**运行期不能再引入同类依赖**；混淆类 `toString()` 会抛异常，日志禁止拼接消息对象 | 上游 M0 实证；本项目自研 gRPC 客户端可绕开，但协议必须严格对齐 |
| **C6** | 华为固件加强 XPM 管控后，旧 so 变体可能加载失败 → 投屏零帧，客户端无法自救 | 上游 v1.0.2 CHANGELOG 实证；属继承风险，需在「关于」页提示 |

> **C7 ~ C9 见附录 C**：三条由 04 号 POC 端到端实测得出、必须照抄的协议级硬约束（字段号 / 配置帧 32 字节 / so 变体表补 7.x）。它们与 C1~C6 同等级，任何实现不得按旧文档猜值。

## 2. 功能需求清单

优先级：**P0** = 没有它软件不可用；**P1** = 核心体验；**P2** = 增强。

| ID | 需求 | 验收标准 | 优先级 |
|---|---|---|---|
| **F-01** | 修复「连接成功后调整窗口大小闪退」 | 连接状态下连续拖动窗口边缘改变尺寸 50 次，进程零崩溃；日志无 `hs_err_pid`；画布尺寸变化时画面不撕裂、不黑屏 | P0 |
| **F-02** | 鼠标滚轮 → 手机上下滑动；鼠标右键 → 手机返回 | 滚轮上/下在手机端各产生一次连续滑动手势（非离散滚轮事件），任意鸿蒙应用可滚动列表；右键单击 = 返回键（键码 2），右键长按不触发 | P0 |
| **F-03** | 主窗口 UI 重设计（Win11 Fluent 风格），重排模拟功能键 | 见 §3 UI 规范；功能键（返回/Home/最近任务/音量/电源）位置可拖动或可配置；界面在 100%/125%/150% 缩放下无错位 | P1 |
| **F-04** | 窗口按手机横竖屏状态自动切换 | 手机旋转 90° 后 1 秒内窗口宽高比自动跟随；旋转过程中不崩溃、不丢帧；横屏时功能键自动改横排布局 | P1 |
| **F-05** | 连接窗口 UI 重设计 + 系统托盘 + 右键菜单 | 连接窗口见 §3；托盘图标常驻，右键菜单至少含「基本设置」「完全退出」；关闭主窗口不退出进程（最小化到托盘），「完全退出」才结束进程并释放 hdc/蓝牙占用 | P0 |
| **F-06** | 断线自动重连 | 手机侧 UNAVAILABLE 断开（上游实测约 9 分钟一次）后自动重连，重连成功 ≤ 5 s，期间 UI 显示「重连中(第 N 次)」；连续失败 5 次转为手动重试并给出原因；网络断开/恢复后能自愈 | P0 |
| **F-07** | 优化画面显示速度与连接动画 | 首帧显示时间 ≤ 1.5 s（POC 实测 794 ms / 1695 ms 两次，上游约 10 s）；画面变化到屏幕呈现的端到端延迟 ≤ 150 ms（同 WiFi 5G）；连接过程有明确进度动画（连接设备 → 拉起投屏 → 等待首帧 → 完成） | P1 |
| **F-08** | 优化电脑输入，优先使用手机自带输入法（参考华为超级终端） | 中文输入时，PC 键盘按键转为**向手机输入法注入字母/拼音**，由手机输入法自己上屏（PC 侧不弹候选）；PC 侧仅作透明的按键转发；特殊键（Ctrl/Alt/Win/多媒体键）可映射；已映射字符直接注入，未映射走文本注入兜底 | P1 |
| **F-09** | 音频同步到电脑，且手机不出声（核心） | 见 §4 详细设计。达成：手机下拉控制中心「音频输出」列表中出现「本电脑」；选中后手机扬声器静音、声音从 PC 播放；可随时切回手机扬声器 | **P0** |
| **F-10** | 画质参数可配置 + 按电脑屏幕比例适配全屏 | 可配置：码率（1~50 Mbps）、帧率（15/30/60）、I 帧间隔、缩放比例、编码质量档；显示模式三档：**等比留黑边 / 裁切填满 / 拉伸变形**；一键全屏（F11）+ 记住上次模式 | P1 |
| **F-11** | 应用内检测更新 + 一键更新（GitHub Releases） | 启动时静默检测 `api.github.com/repos/<owner>/hdc-mirror/releases/latest`；有新版本弹非模态提示（含版本号与更新说明）；点「更新」→ 下载 → 自动安装 → 自动重启，用户只需点一次「允许」；支持跳过此版本；检测失败静默不打扰 | P1 |
| **F-12** | **自适应音画同步**（三档可切，默认自动） | 见 §5。默认 **自动**（Auto）：空闲/出声 → 音画同步，操作中 → 零缓冲跟手；设置页提供 **自动 / 强制音画同步 / 强制低延迟** 三档，切换即时生效并持久化；三档状态下均不出现跳帧、黑屏、音频断续 | P1 |
| **F-13** | **多设备管理**（用户新增，定案：需要） | 见 §3.3。设备卡片列表记住多台手机；每张卡片显示 名称 / 地址 / 在线态 / 最近连接时间；点击卡片即连接，连接中显示进度；离线设备卡片置灰并保留在列表，可「重试」或「移除」；已连接设备卡片高亮并禁止重复连接同一台 | P1 |

## 4. F-09 音频详细设计

### 4.1 方案：PC 端内建蓝牙 A2DP Sink

| 环节 | 实现 |
|---|---|
| 设备发现 | 枚举已配对的蓝牙设备，筛出手机（`BluetoothDevice` + A2DP Sink 能力） |
| 注册为音频接收端 | Windows `Windows.Media.Audio.AudioPlaybackConnection`（WinRT，`AudioPlaybackConnection.TryCreateFromId` + `Open()`） |
| 手机侧呈现 | 手机下拉控制中心「音频输出」出现本电脑名称；选中即把媒体音频路由到 PC，手机扬声器静音 |
| PC 侧播放 | A2DP 流由 Windows 音频栈直接送默认播放设备（无需自己解码） |
| 断开 | `Close()`，手机自动切回扬声器 |

### 4.2 交互流程

1. 首次使用 → 设置页「音频」→「配对新设备」→ 引导用户手机蓝牙搜索本机并配对（一次性）
2. 连接投屏时，若「启用蓝牙音频输出」为开 → 自动 `Open()` 该设备的 AudioPlaybackConnection
3. 状态栏显示「音频：已接管（手机静音）」/「音频：手机外放」
4. 用户随时可在手机上切回扬声器，软件检测到后更新状态，不强行抢回

### 4.3 已知代价（必须在「关于」页如实写明）

| 代价 | 数值 | 处置 |
|---|---|---|
| 音频延迟 | 200~300 ms（SBC 编码，系统级） | 由 F-12 自适应策略吸收；同时给手动滑块 |
| 通话/铃声不走 PC | 协议边界 | 文档说明 |
| 与 2.4G WiFi 互扰 | 明显 | 启动时检测 WiFi 频段，2.4G 时提示「建议切 5GHz」 |
| 一次只能接管一台手机 | A2DP 限制 | 多设备场景下切换设备前先 `Close()` 旧连接，并提示「音频将从 A 设备切到 B 设备」 |
| 需要蓝牙适配器 | 硬件前提 | 无蓝牙时该功能降级隐藏，不影响投屏 |

## 5. F-12 自适应音画同步详细设计

### 5.0 三档策略（决策定案：默认「自动」）

| 档位 | 行为 | 视频缓冲 | 适用 |
|---|---|---|---|
| **自动（默认，Auto）** | 按 §5.1 状态机自动切换，用户无需干预 | 动态 0 / 250 ms | 绝大多数用户；出厂默认 |
| **强制音画同步（ForceSync）** | 恒定音画对齐，永不为输入让路 | 恒为 `audioLatency - videoLatency`（默认 250 ms，可调 100~400） | 看视频、听音乐、投屏观影 |
| **强制低延迟（ForceLowLatency）** | 恒定零缓冲，永不进入同步态 | 恒为 0 ms | 演示操作、录屏教学、对延迟敏感的场景 |

实现要求：

1. 三档为**互斥枚举**（`AvSyncMode.Auto / ForceSync / ForceLowLatency`），持久化到设置，重启保持；
2. 切换即时生效：`Auto → ForceSync` 走 §5.2 的「只丢延迟累积、不补帧」平滑路径；`→ ForceLowLatency` 直接清空视频队列到最新帧；
3. `ForceLowLatency` 下蓝牙音频仍可接管，但明确提示「声音会比画面晚约 250 ms」；
4. `ForceSync` 下操作跟手性下降属预期，不得因此触发 UI 告警；
5. 状态栏始终显示当前生效档位（自动模式下显示状态机实际所在状态）。

### 5.1 状态机（仅「自动」档内部使用）

| 状态 | 进入条件 | 视频缓冲 | 目标 |
|---|---|---|---|
| `Interacting` | 最近 **400 ms** 内收到任意本地输入事件（键/鼠/滚轮/触摸） | **0 ms** | 操作跟手，延迟最小 |
| `Playing` | 蓝牙音频流持续有数据包 **> 300 ms**，且 `Interacting` 已退出 | `audioLatency - videoLatency`（默认 250 ms，可调 100~400） | 音画同步 |
| `Idle` | 无输入、无音频 | 0 ms | 省资源、跟手 |

优先级：`Interacting` > `Playing` > `Idle`。用户一动，立刻退出 `Playing`。

### 5.2 切换平滑策略

- `Interacting → Playing`：目标缓冲从 0 涨到 250 ms，采用「**只丢弃延迟累积、不补帧**」的方式——把 250 ms 内的帧排进队列一次性消化，画面短暂减速 200 ms，不跳帧、不黑屏
- `Playing → Interacting`：立即清空视频队列到最新帧（表现为一次轻微跳帧，用户正在操作时不可感知）
- 状态切换加 200 ms 滞回（hysteresis），避免输入抖动导致状态反复横跳

### 5.3 音频延迟测量

- 首次配对时播放一段 1 kHz 短脉冲 + 记录 RTT，得出近似 `audioLatency`
- 之后每次连接用首包时间戳校准
- 测不准时以手动滑块值为准（设置里给「自动/手动」开关）

### 5.4 风险

| 风险 | 说明 | 缓解 |
|---|---|---|
| A2DP 无全局延迟保证 | 不同手机/编码器差异大 | 提供滑块 + 自动测量，不承诺固定值 |
| 频繁切换可能被感知 | 边看边操作场景 | 滞回 + 最短停留时间 500 ms |
| 视频队列增长导致内存 | 长时 `Playing` | 队列上限 30 帧，超出丢最旧帧 |

### 6.3 设备侧启动流程（自研复刻，参考上游 + POC 实测修正）


## 附录 A：上游实现要点（已核实事实）

**仓库**：`taxiao213/hnscrcpy`，Java 17 / JavaFX 21.0.4 / FFmpeg 7.1-1.5.11（JavaCPP），Apache-2.0，最新 v1.0.3（2026-10-25），单作者，issue 无人回复。

**它本质是华为 `hosScrcpy-1.0.20-beta.jar`（18.86MB）的 JavaFX 外壳**：jar 把 `libscreen_casting.z.so` 推到 `/data/local/tmp/`，用 `uitest start-daemon singleness --extension-name libscreen_casting.z.so -scale 1 -frameRate 30 -bitRate 8388608 -p 5000 -iFrameInterval 2000 &` 拉起；gRPC 走 `hdc fport tcp:<D> localabstract:scrcpy_grpc_socket`。

**proto 只有 3 个 RPC**：`onStart(Empty) returns (stream ReplyMessage)`（唯一视频流）、`onEnd`、`onRequestIDRFrame`。**整条链路没有任何音频接口**——这是 C2 的根因。

**视频格式**：Annex B H.264，4 字节起始码 `00 00 00 01`，每个 gRPC 消息 = 一帧（POC 已逐单元自洽验证），首消息是 SPS+PPS 合包（**精确 32 字节**，见附录 C）；**按屏幕变化推流**（静态画面不发帧，静置 7 秒无帧属正常，不可当断流）；交互时 30 fps；实测吞吐约 0.18~0.3 Mbps；约 9 分钟被设备侧 `UNAVAILABLE` 断开需重连（F-06 要解决的正是它）。

**输入通道**：POC 实测可用路径为 `hdc shell uitest uiInput click|swipe …`（**单次 453–518 ms**，不适合 60 Hz 触摸透传）；按键走子进程 `hdc shell uinput -K -d N -u N`（可多段组合）。

**真机标定键码**（上游 `scripts/spike-keymap.sh` 实测，官方文档有多处是错的）：
最近任务 `2720`（APPSELECT；`2210`/`187` 无效）、Home `1`、Back `2`、电源 `18`、音量−/＋ `16`/`17`、空格 `2050`（非文档值 2052）、方向键 `2012-2015`（文档猜的 `2071-2074` 全错）、TAB `2049`、ENTER `2054`、DEL `2055`、数字 `2000-2009`、字母 `2017-2042`、Shift `2047`。多段可组合：`uinput -K -d 2047 -d 2017 -u 2017 -u 2047` → 'A'。

## 附录 C：POC 实测硬约束补遗（来源 `04-POC验证报告.md`，与 C1~C6 同级）

v1.0 的协议字段全部来自上游文档推测，04 号 POC 用端到端实测推翻了其中三处。**以下三条为强制项，任何"按旧文档猜 tag"的实现都会得到"能连上、能收到、但业务字段全空"的静默故障。**

| ID | 硬约束 | 旧值 / 错误做法 | 实测事实与依据 |
|---|---|---|---|
| **C7（字段号）** | `ReplyMessage.payload` = **field 3**（wire type 2）；`ParamValue.valBytes` = **field 5**；`flags` / `pts` / `len` 全部 = **field 1**（varint） | 文档 `HOS_SCRCPY_PROTOCOL.md:69` 写 `payload = 1`，`valBytes` 按常见写法猜 1。按 1 解析的后果：每条消息都收到、map 永远为空、`data` 长度 0、落盘 0 字节，且**不抛异常** | 原始字节 `1A 2A 0A 04 "data" 12 22 2A 20 <32B>`：`0x1A = (3<<3)\|2` → field 3 wire 2；`0x2A = (5<<3)\|2` → field 5 wire 2；`0x08` → field 1 varint。04 §6.1 |
| **C8（配置帧长度）** | 首条配置帧**精确 32 字节** = SPS 23 B（含 4 字节起始码）+ PPS 9 B（含起始码），`flags = 8` | 文档写「约 33 字节」。按「必须 33」做断言会误判，把正常首帧当异常丢弃 → 解码器永远拿不到 SPS/PPS | 04 §6.2、§5 帧长表（min=32 / max=39431 / avg=9070） |
| **C9（so 变体表）** | 变体选择表**必须补 7.x 行**：uitest `7.0.0.1` → 直接使用 `libscrcpy_server_unix_6.8-20260801.z.so`（247,989 B，实测可用）；判定顺序为「**md5/字节数匹配优先，版本映射兜底**」 | 上游规则只覆盖到 6.5（≥6.0.2.1 → 6.3.1/6.4/6.5），遇到 7.0.0.1 会选不到任何变体而直接失败 | 04 §6.7、§2 环境表（设备端 uitest 7.0.0.1，so 字节数与 6.8 变体一致） |

### C.1 附带的实现约束（同源实测，写入代码规范）

| 项 | 要求 |
|---|---|
| gRPC 通道 | h2c 明文需 `AppContext.SetSwitch("System.Net.Http.SocketsHttpHandler.Http2UnencryptedSupport", true)`；`MaxReceiveMessageSize` 抬到 **100 MB**（默认 4 MB，IDR 一大就炸） |
