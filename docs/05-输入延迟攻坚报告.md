> 日期：2026-11-11

> 代码：`src/poc2/`（`C:\dotnet8\dotnet.exe build` exit 0）

## 0. 结论先行

**跟手拖拽可行，而且余量很大。**

| 指标 | 改造前（当前 POC） | 改造后（本报告方案） | 提升 |
|---|---|---|---|
| 单次点击 P50 | **412.7 ms** | **3.4 ms**（pipelined） | **121×** |
| 单次点击 P50（逐条等响应） | 412.7 ms | **49.6 ms** | 8.3× |
| 单次点击 P95 | 628.4 ms | 71.6 ms（顺序）/ 3.4 ms（流水） | 9–185× |
| 注入吞吐 | 2.4 次/秒 | **296 次/秒** | **123×** |
| 触摸事件（touchMove）能力 | **无**（`uitest uiInput` 没有 down/move/up） | **60Hz 零背压，可到 200Hz+** | 从 0 到 1 |

一句话：**把 `hdc shell uitest uiInput click` 换成设备侧 uitest daemon 的 8012 JSON-RPC 长连接，延迟从 448 ms 降到 3.4 ms（流水）/ 49.6 ms（同步），并且第一次拿到了真正的 touchDown/touchMove/touchUp 触摸流。**

三条路径的物理上限（实测，不是估算）：

```
现状   hdc.exe 启动 + TCP + shell 会话 + uitest 进程启动 + 注入
       └── 153ms ───┘         └── 260ms ──┘   └─ 50ms ─┘   = 448~518ms
常驻 shell  去掉 153ms，但仍要起 uitest 进程 260ms
       └────────────── 天花板 ≈ 310ms/次，永远达不到 100ms ──────────────┘
8012 RPC   去掉 hdc 进程、shell 会话、uitest 进程启动 —— 只剩一次 TCP 往返
       └────────────── 3.4~50ms，达标 ──────────────┘
```

## 1. 阶段一：把 448 ms 拆开

### 1.1 五种方式单次往返（PowerShell 计时，各 20 次，点击点 600,1400）

| # | 方式 | min | **P50** | P95 | max | avg |
|---|---|---|---|---|---|---|
| M0 | `hdc list targets`（纯 hdc 进程启动基线） | 64.7 | **73.8** | 83.3 | 94.5 | 74.5 |
| M1 | `hdc shell "uitest uiInput click 600 1200"`（每次新进程）| 378.2 | **447.6** | 559.3 | 568.0 | 462.3 |
| M1b | `hdc shell "echo hi"`（同样新进程，不注入） | 135.4 | **153.3** | 197.6 | 198.3 | 159.2 |
| M2 | 一次 shell 跑 **2 条** click | 712.1 | **770.2** | 794.4 | 834.2 | 765.3 |
| M2b | 一次 shell 跑 **5 条** click | 1615.3 | **1702.6** | 1766.8 | 1775.7 | 1702.5 |
| M4 | 不带 `-t` 的 `hdc shell echo` | 118.2 | 154.2 | 198.9 | 199.6 | 159.8 |
| M5 | `hdc tconn` 重连 | 66.5 | 71.9 | 84.9 | 84.9 | 72.9 |

**读法：**
- M1 − M1b = **294 ms** 是 `uitest` 进程启动 + 注入的净成本。
- M1b − M0 = **79 ms** 是 hdc 的 shell 会话建立成本（hdc 进程启动 74 ms 之外）。
- M2 第二条 click 只多 **322 ms**（几乎等于第一条），说明**"一次 shell 跑多条"省不到注入成本，只省掉一次建连**。
- M4 ≈ M1b ⇒ `-t <target>` 不带来可测的额外开销，不能靠它优化。
- M5 = 72 ms ⇒ tconn 常连已生效，**建连本身不是瓶颈**（瓶颈在 hdc 每次仍要新起进程）。

### 1.2 斜率法：把 448 ms 逐层剥开

同一次 `hdc shell` 内跑 8 遍（PC 侧计时，一次 shell 基线 141 ms）：

| 循环体 | 每次边际成本 | 它说明了什么 |
|---|---|---|
| `/bin/echo x` | **35.3 ms** | 设备 fork 一个进程只要 35 ms，不贵 |
| `uitest --version` | **259.3 ms** | **`uitest` 这个 962 KB 二进制自身启动就要 260 ms**（还没注入任何东西） |
| `uitest uiInput help` | **266.7 ms** | 同上，和注入无关 |
| `uitest uiInput click 600 1200` | **312.4 ms** | **真正的注入只额外花 45–50 ms** |

单次计数验证（同一次 shell 内）：1 click 421 ms、2 click 805 ms、4 click 1471 ms、8 click 2641 ms。

**⇒ 448 ms 的真实构成：**

```
hdc.exe 进程启动            ~74 ms   ← 换常驻 shell 可省
+ TCP + shell 会话建立      ~79 ms   ← 换常驻 shell 可省
+ uitest 二进制启动         ~260 ms  ← 常驻 shell 省不掉（每次仍是新进程）
+ 真正的手指注入            ~50 ms   ← 本该有的成本
─────────────────────────────────
= 448 ms
```

**结论：常驻 hdc shell 的天花板是 310 ms/次，单靠它永远进不了 100 ms。** 要达标必须换通道，不能只优化 hdc 的用法。

### 1.3 常驻交互式 shell：hdc 3.2.0c 明确不支持

按要求试了五种写法（`probe_shell_mode.ps1`），全部失败：

- `hdc shell` 不带命令 → `[W][...] Not support stdio TTY mode` 后退出；
- stdin 被管道接管 → hdc 退回自己的控制台并回 `Unknown operation command...`；
- `hdc` 无参 + 管道 stdin → 同样 `Unknown operation command...`。

poc2 的 `HdcShellSession.TryStartPersistentAsync()` 会把这段原文抓下来作为证据：

```
✗ 常驻 shell 不可用：写入 2500ms 内无哨兵响应；
  tail: [W][2026-11-11 00:34:49] Not support stdio TTY mode
```

**⇒ 任务书里设想的"常驻 hdc shell + 哨兵配对"这条路在 hdc 3.2.0c 上物理不存在。**

### 1.4 顺带测到的：并行注入

| 并发数 | 总墙钟 | 平均每条 | 理论吞吐 |
|---|---|---|---|
| 2 | 580 ms | 290.2 ms | 3.4/s |
| 4 | 521 ms | 130.3 ms | 7.7/s |
| 8 | **663 ms** | **82.8 ms** | 12.1/s |
| 12 | 941 ms | 78.4 ms | 12.8/s |
| 串行 8 条对照 | 3996 ms | 499.5 ms | 2.0/s |
| 12 条纯 `echo`（通道上限） | 330 ms | 27.5 ms | — |

进程启动是 CPU 密集、可并行，所以"并发 8 条"能把均摊压到 82.8 ms。但这是**吞吐**不是**延迟**——单次 click 仍要 300 ms 以上才生效，对跟手毫无用处（而且并发点击是乱序的，对触摸流是灾难）。

## 2. 决定性发现：设备侧 uitest daemon 的 8012 JSON-RPC 通道

设备上常驻的 `uitest start-daemon`（上游 hnscrcpy 起的 PID 15201）在设备 `tcp:8012` 监听一个 JSON-RPC 服务。上游已经用 `hdc fport tcp:36987 tcp:8012` 把它转到本机。**只发请求、不改任何配置**，实测：

### 2.1 线格式（裸 TCP，无 HTTP、无 TLS）

```
┌────────────────────────────────────┬──────────────┬──────────────┬────────────────────────────────────┐
│ "_uitestkit_rpc_message_head_" 28B │ len: 8B 大端 │ JSON (UTF-8) │ "_uitestkit_rpc_message_tail_" 28B │
└────────────────────────────────────┴──────────────┴──────────────┴────────────────────────────────────┘
响应：裸 JSON，没有 head/tail 包裹，多个响应首尾直接相连 → 必须自己按花括号配平切分
```

三种 `method`：

```jsonc
// ① 调 Hypium Driver API
{"module":"com.ohos.devicetest.hypiumApiHelper","method":"callHypiumApi",
 "params":{"api":"Driver.getDisplaySize","this":"Driver#0","args":[]}}

// ② 触摸事件（关键）
{"module":"com.ohos.devicetest.hypiumApiHelper","method":"Gestures",
 "params":{"api":"touchDown","args":{"x":630,"y":1700}}}

// ③ 截图 / UI 树
{"module":"com.ohos.devicetest.hypiumApiHelper","method":"Captures", ...}
```

- `module` **必须是包名** `com.ohos.devicetest.hypiumApiHelper`，写别的会被拒。
- 每个请求在 daemon 里是独立 session，hilog 每次都会打 `A03100/uitest/UiTestKit_Addon: SessionDeath3!`，**这是设计如此，不是错误**。

### 2.2 延迟实测

| 测法 | P50 | P95 | min | max |
|---|---|---|---|---|
| `Driver.getDisplaySize` ×10（PowerShell 客户端，长连接） | 30.4 | — | 14.8 | 74.8 |
| `Driver.getDisplaySize` ×10（**C# 客户端**，长连接） | **7.2** | 51.4 | **6.1** | 51.4 |
| `touchMove` ×100（顺序等响应） | 30.3 | 76.0 | 13.2 | 77.5 |
| `touchDown` / `touchUp` | 31–77 | — | — | — |

C# 客户端比 PowerShell 快 4 倍（PowerShell 的 `DataAvailable` 轮询要睡 1–5 ms，且每次 `Get-Date` 都走一遍 COM）。**真实数字看 C# 那一行。**

### 2.3 保序 + 零背压（跟手的关键）

- **保序**：交错发 10 帧 `getDisplaySize` / `getDisplayDensity`，响应严格是 `S,D,S,D,S,D,S,D,S,D`。
- **零背压**：一口气写 20 帧 touchMove → **20 个响应 75 ms 全部回来，均摊 3.8 ms/帧**。
- **60Hz 持续流**：touchDown + 120 帧 touchMove（按 16.7 ms 节奏）+ touchUp，
  - 墙钟 2008 ms（目标 2004 ms，节奏精确）；
  - 单帧写入耗时 **P50 = 0.07 ms，max = 1.23 ms**（TCP 缓冲从不回压）；
  - 尾部排空 **46 ms**（122 个响应全部归位）。

**⇒ 设备侧处理能力远超 60Hz（实测 266 帧/秒的批处理能力，296 次点击/秒）。所谓"跟手"的上限不在设备，而在这条链路的 RTT（本机到手机约 3–10 ms）。**

### 2.4 注入真实性（每次都截图目视确认过）

| 测试 | 结果 | 验证方式 |
|---|---|---|
| 6 步 `touchDown→touchMove×4→touchUp`（上滑 100px） | 评论区真实滚动 | 前后两帧像素采样 8568 点，差异 1151 点（13.4%），底部露出新评论 |
| 100 步 `touchMove` | 评论区真实滚动 | 同上，差异 1154 点 |
| `uitest uiInput swipe 630 60 630 1600 800` | 通知栏被拉下 | 截图目视，`keyEvent Back` 可收起 |
| `uitest uiInput click 600 1400` | 落进小红书评论框并弹键盘 | 截图目视 |
| `Driver.pressHome` / `Driver.pressBack` | 真回桌面 / 真返回 | 截图目视 |

> ⚠️ **`docs/03-设备侧能力实测清单.md` §5.4 / §6.3 的"uInput 与 Gestures 假成功"结论对当前设备与系统版本已经过时。**
> 那份结论当时依据的是 `hidumper` 里 MMI 29201 `operation not permitted` 与"前台 bundle 未变"，但本次在同一台机器上、用同样的调用方式，肉眼可见地改变了屏幕内容。

### 3.1 `HdcShellSession` —— 按要求实现，但如实降级

```csharp
var shell = new HdcShellSession(hdcPath, device, defaultTimeoutMs: 4000);

bool ok = await shell.TryStartPersistentAsync();   // 探测常驻 shell（本 hdc 版本返回 false）
string? why = shell.PersistentRejectReason;        // 失败原因，含 hdc 原始报错

TimeSpan t = await shell.InjectAsync("uitest uiInput click 600 1400"); // 自动选最快可用形态
```

实现要点（都是踩过的坑）：

1. **三种形态自动降级**：`persistent` → `batch` → `oneshot`。
2. `ProcessStartInfo` 必须 `UseShellExecute=false` + `CreateNoWindow=true` + `RedirectStandardInput/Output/Error=true`，少一个就弹窗或死锁。
3. **stdout 和 stderr 必须同时读**（`PumpAsync` 跑两个 Task）——hdc 往 stderr 打 `[I]/[W]` 日志，只读 stdout 会在长时间跑批时因管道写满而挂死。
4. **哨兵必须整行前缀匹配**（`line.StartsWith("__DONE__")`），不能用 `Contains`：hdc 会回显你写进去的命令行，`Contains` 会把自己写的那句当哨兵，立刻"成功"。
5. **超时会让响应错位**，所以超时后必须 `KillPersistentAsync()` 重建会话，并把所有挂起 waiter 置异常，不能只跳过当前这一条。
6. 命令里不要嵌套引号：`hdc shell "a \"b\""` 在 Windows 上会被再剥一层壳。

> 本机实测：`persistent` 不可用（`Not support stdio TTY mode`），`batch` 一次跑 8 条能把单条摊到 **320.1 ms**，`oneshot` 是 **412.7 ms**。两者都到不了 100 ms。

### 3.2 `UitestRpcClient` —— 跟手的实现

```csharp
await using var rpc = new UitestRpcClient("127.0.0.1", 15002); // 本地 fport 端口
await rpc.ConnectAsync();

// ① 同步：发一条等一条（P50 49.6 ms / 单次点击）
TimeSpan t = await rpc.ClickAsync(x, y);

// ② 流水：入队即走，不等响应（3.4 ms/次，296 次/秒）
var pending = new List<Task<string>>();
for (...) pending.Add(rpc.QueueGestureAsync("touchMove", x, y));
await Task.WhenAll(pending);          // 只在需要对齐时才等

// ③ 一次性手势（设备侧合成，不跟手）
await rpc.SwipeAsync(x1, y1, x2, y2, speed: 2000);

// ④ 读屏
var (w, h) = await rpc.GetDisplaySizeAsync();
```

设计要点：

| 关注点 | 做法 | 为什么 |
|---|---|---|
| 响应切分 | UTF-8 `Decoder` 增量解码 + 花括号配平（跟踪 `inString` / `escape`） | 响应无框架，多个 JSON 首尾相连，还可能跨 TCP 包 |
| 请求-响应配对 | FIFO 队列 + `TaskCompletionSource` | 设备保序（已实测），所以不需要 id；帧里也没地方放 id |
| 保序 | 所有写入走同一个 `_writeGate`，入队与发送在同一临界区完成 | 并发调 `QueueXxx` 时不会被 write 顺序打乱 |
| 超时 | 单个请求超时 → 整条连接作废 → `ReconnectAsync()` | 一条超时会让后面所有响应错位一格，逐条容错是错的 |
| 掉线 | 读循环 `finally` 里 `FailAllPending()`，把所有挂起请求置异常 | 否则调用方永远挂着 |
| `NoDelay` | `TcpClient.NoDelay = true` | 一个触摸帧只有几十字节，Nagle 会硬生生加 40 ms |

### 3.5 拖拽方案对比

| 方案 | 耗时 | 跟手 | 说明 |
|---|---|---|---|
| ① `uitest uiInput swipe` | 1050 ms（1540px 时 3168 ms） | ✗ | 260 ms 进程启动 + 手势全时长阻塞，手势期间无法干预 |
| ② `RPC Driver.swipe` | 789 ms | ✗ | 没有进程启动，快了 25%，但手势一旦发出就必须走完，中途改不了方向 |
| ③ **`RPC` 分步 touchMove** | 与手势时长同阶（1091 ms / 60 帧） | **✓** | 每帧独立，可随时改方向、可中途反悔、可做惯性跟随 |

**结论：只有 ③ 是真触摸透传。①② 只能做「一次性动作 + 本地乐观渲染」。**

为什么 ③ 的总耗时看起来不比 ② 短：因为 ③ 是**按 60Hz 节奏实时跑**的（60 帧 × 16.7 ms = 1000 ms），而 ② 是设备侧一次性合成。体验差别不在总时长，在于**③ 在拖拽过程中画面每一帧都在跟随手指，② 在拖拽过程中画面是死的**。

## 4. 阶段三：能不能跟手？

### 能，而且余量足够做 120Hz

| 判据 | 目标 | 实测 | 判定 |
|---|---|---|---|
| 单次注入延迟 | < 100 ms | **3.4 ms**（流水） / **49.6 ms**（同步） | ✅ 达标 29× |
| 触摸事件粒度 | 需要 down/move/up | **三种都有**，且真实生效 | ✅ |
| 触摸事件频率 | ≥ 60Hz | **296 次/秒**，60Hz 流零背压（单帧写入 0.07 ms） | ✅ 4.9× 余量 |
| 事件保序 | 必须保序 | **严格保序**（10 帧交错发，响应 S,D,S,D…） | ✅ |
| 掉线恢复 | 自动重建 | `ReconnectAsync()` + `FailAllPending()` | ✅ |
| 长时稳定性 | — | 801 帧收发、0 次重连 | ✅ |

**链路预算（跟手的真实延迟拆解）：**

```
本地鼠标/触摸事件        0 ms
→ 本机 → 手机 TCP RTT    3~10 ms   ← 这一跳是物理下限，改不了（可上 WebRTC/QUIC 也只是省一点）
→ 设备 daemon 处理       <1 ms     ← 实测 266 帧/秒批处理，几乎免费
→ MMI 注入 + 合成        ~0.5 帧   ← 一个 vsync
────────────────────────────────────
总计                     5~15 ms   ⇒ 远低于人眼可感知的 ~50 ms 阈值
```

### 瓶颈归因（澄清：剩下的延迟都不在 hdc 协议上）

| 环节 | 是否是瓶颈 | 证据 |
|---|---|---|
| hdc 协议 / 建连 | **是（改造前）** | 每次 `hdc.exe` 进程启动 74 ms + shell 会话 79 ms；tconn 常连后仍有 74 ms/次 |
| `uitest` 二进制启动 | **是（改造前，最大头）** | `uitest --version` 空转就要 259.3 ms，与注入无关 |
| 设备侧 MMI 注入 | **不是** | `touchMove` 单帧 0.5 ms 级，批处理 266 帧/秒 |
| 8012 RPC 通道 | **不是** | 同步 49.6 ms / 流水 3.4 ms |

### 推荐方案排序

1. **【首选】8012 JSON-RPC 长连接 + 60Hz 触摸流**（本报告方案）
   单次 3.4 ms，跟手，已跑通，代码在 `src/poc2/UitestRpcClient.cs`。
2. **【次选】8012 RPC 的 `Driver.swipe` 一次性手势 + 本地乐观渲染**
   延迟可接受（789 ms 的拖拽过程里本地预览跟着鼠标动），但拖拽中途不可改向，做不了"甩动惯性""画圈选择"。
3. **【兜底】现有 `uitest uiInput` 一次性动作**
   仅在 8012 通道完全不可用时使用（例如设备上 daemon 起不来）。P50 412.7 ms。

**设备侧常驻 daemon 不需要你自己写** —— uitest 自带的 daemon 已经是常驻的，问题只是"别每次都重启 uitest 进程去跟它说话"。

## 5. 落地要点（给生产代码的清单）

### 5.1 启动顺序

```csharp
// ① 确保设备上有 uitest daemon（singleness = 单实例，已存在则复用）
//    hdc -t <dev> shell "uitest start-daemon singleness"
//    ⚠️ 如果上游 hnscrcpy 已经起了（PID 15201），直接复用，不要重复起

// ② 建本地端口转发（用一个不冲突的本地端口，别抢上游的 36987）
//    hdc -t <dev> fport tcp:15002 tcp:8012

// ③ 连本地端口，长连接常驻
var rpc = new UitestRpcClient("127.0.0.1", 15002);
await rpc.ConnectAsync();

// ④ 退出时清掉自己建的转发（只删自己那条）
//    hdc -t <dev> fport rm tcp:15002 tcp:8012
```

实测确认：**自建 fport 完全独立可用**（`tcp:15002 → tcp:8012` 47 ms 探活成功），不需要依赖上游那一条。

### 5.2 触摸流的正确写法

```csharp
// ✗ 错：一条一条 await（30~50ms/帧，上限 20Hz，拖拽会顿）
foreach (var p in points)
    await rpc.GestureAsync("touchMove", p.X, p.Y);

// ✓ 对：入队即走，按 16.7ms 节奏推，最后统一对齐
var pending = new List<Task<string>>();
var sw = Stopwatch.StartNew();
for (int i = 1; i <= frames; i++)
{
    pending.Add(rpc.QueueGestureAsync("touchMove", x, y));   // 写入 0.07ms，不阻塞
    double target = i * 1000.0 / 60.0;
    if (target > sw.Elapsed.TotalMilliseconds)
        await Task.Delay((int)(target - sw.Elapsed.TotalMilliseconds));
}
await Task.WhenAll(pending);                                 // 只在收尾时对齐
```

**必须做的三件事：**
1. `touchDown` 一定要配对 `touchUp`——丢一个 `touchUp`，设备就处于"手指按住不放"状态，用户会觉得手机卡死。
2. 指针离开窗口 / 松手 / 异常中断时，**发一个兜底的 `touchUp`**（哪怕坐标是最后已知位置）。
3. 拖拽结束不要立即 `touchUp`，按真实的速度补几帧（惯性），否则甩动没手感。

### 5.3 不能用的做法

- ❌ 用 `Driver.swipe` 做拖拽（中途改不了方向）。
- ❌ 并发 `await` 多条 `GestureAsync`（保序虽在，但你会失去节奏控制，且延迟抖动变大）。
- ❌ 每次拖拽重建连接（建连本身 5~10 ms，但会丢 daemon session，且 hilog 噪声大）。
- ❌ 用 `hdc shell uitest uiInput ...` 做任何需要跟手的操作（物理上做不到）。

## 6. 遗留问题与后续

| # | 事项 | 说明 |
|---|---|---|
| 1 | **daemon 由谁起** | 生产环境要自己保证 `uitest start-daemon singleness` 在跑。若上游 hnscrcpy 也在跑，复用即可（singleness 保证单实例）。需要在客户端启动时探测 `tcp:8012` 是否可连，不可连则起 daemon + fport。 |
| 2 | **fport 端口分配** | 别硬编码 15002，从 15000 起扫一个空闲端口，退出时必须 `fport rm`，否则设备上会残留转发。 |
| 3 | **多指触控未验证** | 本次只测了单指。`Gestures` 有 `ButtonLeft/Middle/Right`、`MouseMove`、`AxisDown`，多指需要看 Hypium 是否有 `touchDown` 的 pointerIndex 参数，未测。 |
| 4 | **`Captures.captureLayout` 未在本轮用于坐标换算** | 116–198 KB UI 树，可用来做"点在哪"的语义定位。视频流侧应有独立的坐标映射（投屏分辨率 → 设备分辨率），本次未涉及。 |
| 5 | **屏幕锁定状态下的注入** | 本轮测试末段设备自动锁屏，未验证锁屏时 `Gestures` 是否仍生效（`Driver.wakeUpDisplay` 返回成功但不真唤醒）。生产上应假设锁屏时注入被丢弃。 |
| 6 | **docs/03 需要修订** | §5.4 / §5.5 / §6.3 关于"uiInput 假成功"与"8012 60.3ms"的结论已过时，见本报告 §2.4。 |
