## 1. 设备侧启动流程

### 1.1 先说最反直觉的一点：上游 Java 不做任何启动动作

对 `src/main/java` 全量 grep `uitest|start-daemon|--version|push|/data/local/tmp|libscreen_casting`，命中只有 4 条**注释**（`CliOptions.java:38`、`:70` 是 CLI 自己的 `--version`；`TextInjector.java:20`、`:26` 是文本注入注释；`CoordinateMapper.java:50`、`DeviceController.java:9`、`InputForwarder.java:16` 是通道说明）。也就是说：

- 没有 `.so` 推送代码；
- 没有 `hdc fport` 调用（`device/HdcClient.java:131-145` 定义了 `fport`/`fportRemove`，但 **main 代码零调用**，只有 `src/test/java/com/hnscrcpy/device/HdcClientTest.java:63-72` 在测它）；
- 没有 `uitest start-daemon`；
- 没有 uitest 版本检查、没有 md5 变体匹配、没有失败重试。

全部由内置 jar 的 `HosRemoteDevice` 内部完成。上游能做的只有三件事：定位 jar → `URLClassLoader` 加载 → 反射构造对象并 `startCaptureScreen`。

```java
// src/main/java/com/hnscrcpy/stream/HosScrcpyBridge.java:42-60（节选）
URLClassLoader loader = new URLClassLoader(new URL[]{jar.toUri().toURL()},
        ClassLoader.getSystemClassLoader());
Class<?> configCls = loader.loadClass(PKG + "HosRemoteConfig");   // PKG = "com.huawei.hosscrcpy.api."  (L31)
Object cfg = configCls.getConstructor(String.class).newInstance(sn);
configCls.getMethod("setHdcPath", String.class).invoke(cfg, hdcPath);
configCls.getMethod("setFrameRate", int.class).invoke(cfg, video.fps());
configCls.getMethod("setBitRate", int.class).invoke(cfg, video.bitRateMbps());
configCls.getMethod("setIFrameInterval", int.class).invoke(cfg, video.iFrameIntervalMs());
configCls.getMethod("setScale", int.class).invoke(cfg, video.scale());
device = deviceCls.getConstructor(configCls).newInstance(cfg);
```

`HosScrcpyStream.start()` 里唯一一句真正的设备侧动作是：

```java
// src/main/java/com/hnscrcpy/stream/HosScrcpyStream.java:58
bridge.startCaptureScreen(bridge.newCallback(sink));   // → HosScrcpyBridge:100-101 反射 jar 的 startCaptureScreen
```

**对 C# 的直接含义**：第 1 章描述的全部步骤，在 C# 里必须自己从零实现，蓝本是 `docs/HOS_SCRCPY_PROTOCOL.md:32-56` 的逆向结论，而不是上游 Java。

### 1.3 `uitest start-daemon singleness` 每个参数的含义与取值范围

命令原型（`docs/HOS_SCRCPY_PROTOCOL.md:43-49`，由 `HosRemoteConfig.getParams()` 生成）：

```bash
/system/bin/uitest start-daemon singleness \
  --extension-name libscreen_casting.z.so \
  -scale 1 -frameRate 30 -bitRate 8388608 \
  -p 5000 -iFrameInterval 2000 &
```

| 参数 | 含义 | 取值范围 / 单位 | 上游实际取值 | 定位 |
|---|---|---|---|---|
| `singleness` | 单实例管道模式（daemon 的单会话形态） | 固定字面量 | 固定 | `docs/HOS_SCRCPY_PROTOCOL.md:43` |
| `--extension-name` | 要加载的扩展 so 名（设备侧路径的 basename） | 与推送的变体文件名一致 | `libscreen_casting.z.so` | 同上 |
| `-scale` | 分辨率缩放比 | 整数倍率，1 = 原始分辨率 | `VideoConfig.scale()` = **1**（默认） | `stream/VideoConfig.java:15-17` |
| `-frameRate` | 目标帧率 | 整数 fps | `VideoConfig.fps()` = **60**（默认；文档示例写的 30 是另一次采集） | `stream/VideoConfig.java:15-17`、`util/AppConfig.java:29` |
| `-bitRate` | 码率 | 入参 **Mbps**，jar 内部 `bitRate << 20` 转字节 | `VideoConfig.bitRateMbps()` = **30** | `stream/VideoConfig.java:15-17`、`util/AppConfig.java:28` |
| `-p` | 旧版监听端口 | tcp 端口 | `5000`；**6.5 变体已 deprecated，改为 unix abstract socket** | `docs/HOS_SCRCPY_PROTOCOL.md:43-49` |
| `-iFrameInterval` | IDR 间隔 | **毫秒** | `VideoConfig.iFrameIntervalMs()` = **2000** | `stream/VideoConfig.java:15-17` |

C# 侧注意两点：

1. **码率单位是 Mbps 的十进制值**，`30` 意味着设备侧最终收到 31457280 bit/s —— 30 Mbps 对 1272×2860@60 是偏高的（文档示例只用了 8 Mbps），首版建议 8，再按需上调。
2. `-p 5000` 在新变体上无效，真正可用的是 fport 到 `localabstract:scrcpy_grpc_socket`；但**该参数仍需带上**（命令模板固定）。
3. `VideoConfig.maxSize` 字段在 record 里存在（默认 1600）但 **生产路径从不使用**：`HosScrcpyBridge` 没有调用 `setImageScaleSize`（`stream/HosScrcpyBridge.java:42-60` 里没有这一行），`-m/--max-size` 的 usage 也自认"预留"（`cli/CliOptions.java:65`）。

### 1.4 fport 端口如何分配

【文档 `docs/HOS_SCRCPY_PROTOCOL.md:35`、`:50-52`、`:94-101`】

- 本地端口 **随机取 36000–36999**，用于 gRPC 转发（称 D）。
- uitest agent 需要 **3 条** fport（B=控制、C=layout、D=JPEG 截图），也是随机本地端口。
- 命令形态：
  - gRPC：`hdc fport tcp:<D> localabstract:scrcpy_grpc_socket`（uitest ≥6.0.2.1）/ `hdc fport tcp:<D> tcp:5000`（更旧）；
  - agent <1.2.0：`hdc fport tcp:<port> tcp:8012`；agent ≥1.2.0：`hdc fport tcp:<port> localabstract:uitest_socket`。
- 客户端连接目标写法固定为 `dns:///127.0.0.1:<D>` + `usePlaintext()`，`maxInboundMessageSize = 100MB`（`:53-54`）。
- 清理：`hdc fport rm tcp:<port>` 逐条撤（`:141-145`），并 `ps -ef | grep singleness` 找带 `--extension-name` 的进程 `kill -9`，最后 `sleep 2`（防止新旧实例抢同一 socket）。

**范围本身没有限制**：端口是随机高位端口，`.so` 是单例，所以**同一台设备只能有一条会话**（印证 `App.java:60-61` 的 `mirrorWindows` 注释"设备侧 scrcpy 单例"与 `PRD.md` 的 F13 条）。

`device/HdcClient.java:131-145` 给出了 C# 可直接复用的命令行形态（虽然上游 main 不调用）：

```java
// device/HdcClient.java:131-136
List.of(hdc.toString(), "-t", sn, "fport", "tcp:" + localPort, remote)   // remote 形如 "localabstract:scrcpy_grpc_socket"
// device/HdcClient.java:140-145
List.of(hdc.toString(), "-t", sn, "fport", "rm", "tcp:" + localPort)
```

### 1.6 启动失败如何判定与重试

上游 client 侧**没有启动失败判定**，只有"结果判定"：`startCaptureScreen` 抛异常 → 会话进入 ERROR（`session/MirrorSession.java:210-217`），状态栏显示"启动失败: msg"（`ui/MirrorWindow.java:130-160`）。jar 内部的失败检测（`hdc list targets` 5s 超时误判、`uitest --version` 不达标、md5 不匹配的推送失败）**未确认**：jar 未反编译，仅有文档描述 `docs/HOS_SCRCPY_PROTOCOL.md:34` 提到"超时仅 5s，偶发误判 → M2 加重试"。

C# 侧必须自己补齐的重试点（这些在 Java 侧是空白）：

1. `hdc list targets` 5s 超时误判 → 至少重试 2 次（`docs:34` 明确建议）；
2. 推送 `.so` 后校验设备端 md5；
3. `start-daemon` 之后必须轮询"fport 端口可连"（TCP connect 成功即就绪），不能靠固定 sleep；
4. 清理失败留下的孤儿 `singleness` 进程再重启（`docs:141-145`）。

### 2.2 payload 的实际 key 与语义（这是 C# 必须照抄的契约）

`docs/HOS_SCRCPY_PROTOCOL.md:72-77`：

| key | 类型 | 含义 | 上游是否读取 |
|---|---|---|---|
| `data` | `bytes`（`valBytes`） | **Annex B H.264 访问单元**，以 4 字节起始码 `00 00 00 01` 开头 | 由 jar 解析后经 `onData(ByteBuffer)` 回调给 Java（`stream/HosScrcpyBridge.java:78-81`） |
| `pts` | 未确认（推测整数） | 显示时间戳 | Java 侧不使用（`VideoFrame.ptsMicros` 恒由解码器给出） |
| `flags` | 未确认 | 帧标志（如关键帧） | Java 侧不使用 |
| `len` | 未确认 | 数据长度 | Java 侧不使用 |

`HosScrcpyBridge.dispatch` 只处理三个回调名，其余一概忽略：

```java
// src/main/java/com/hnscrcpy/stream/HosScrcpyBridge.java:73-88
switch (name) {
    case "onReady"     -> { sink.onStreamReady(); return null; }
    case "onData"      -> { ByteBuffer bb = (ByteBuffer) args[0];
                            byte[] data = new byte[bb.remaining()];
                            bb.duplicate().get(data);
                            sink.onH264Frame(data); return null; }
    case "onException" -> { sink.onStreamError((Throwable) args[0]); return null; }
    default -> { return null; }
}
```

### 2.3 调用序列（C# 客户端应实现的时序）

1. 建立 channel → `onStart(Empty)`，**同步拿到 stream 后立即开始收**；
2. 流上第一条消息 = SPS+PPS 合包（≈33 字节），后续每条消息 = 一个完整 AU；
3. 需要关键帧时另发一元调用 `onRequestIDRFrame(Empty)`；
4. 结束会话发 `onEnd(Empty)`，然后关闭 channel + 撤 fport。

### 2.4 ★ 音频能力结论：**否，协议里没有任何音频**

三条独立证据链，任一成立即足够：

1. **proto 层面**：`ScrcpyService` 只有 `onStart`/`onEnd`/`onRequestIDRFrame` 三个 rpc，返回的 `ReplyMessage` 只有一个 `map<string, ParamValue>`，实际 key 只有 `data/pts/flags/len`（`docs/HOS_SCRCPY_PROTOCOL.md:60-77`）。没有任何 audio / pcm / opus / aac 字段、没有 codec 协商 message、没有第二路 stream。
2. **载荷层面**：`data` 被明确描述为 "Annex B H.264"，且"每个 gRPC 消息 = 一帧"（`docs:72-77`）。同一通道里没有多路复用第二类媒体。
3. **实现与声明层面**：Java 源码全仓 grep `[Aa]udio|AUDIO|音频|PCM|opus|Opus|AAC|aac` 仅 6 处命中，全部是文档声明或第三方许可清单，源码 **0 处**：
   - `README.md:121` `- 音频转发暂不支持（hosScrcpy 无音频通道）`
   - `docs/PRD.md:54` `- 音频转发（hosScrcpy 不支持）`
   - `docs/RELEASE_NOTES_v1.0.0.md:37`、`v1.0.1.md:31`、`v1.0.2.md:30` `- **不支持音频转发**（投屏组件无音频通道，仅画面+远控）`
   - `THIRD-PARTY-NOTICES.md:43` 只是 FFmpeg 构建里带了 Opus/Speex 编解码库的许可清单，与协议无关。

**推论（对 C# 产品）**：走"hosScrcpy 同款协议"这条路，音频必须换实现路径，协议侧没有任何可钩的点。上游自己也从未尝试过——`docs/PRD.md:54` 直接列为"暂不做"。

## 3. 视频帧处理

### 3.1 Annex B 如何切分：靠**消息边界**，不靠起始码扫描

这是最容易写错的地方。上游**生产路径完全不切分**：

- `H264Decoder.splitAccessUnits(byte[])`（`decode/H264Decoder.java:285-311`）**只被单测使用**：`src/test/java/com/hnscrcpy/decode/H264DecoderTest.java:28/89/111/125/146/159`、`DecoderPumpLiveTest.java:28`、`DecoderPumpParamSetsTest.java:31/68`、`DecoderPumpResolutionChangeTest.java:54`、`DecoderPumpRestartTest.java:29`、`RenderSchedulerTest.java:47`。main 代码零调用。
- 生产路径是：**每条 gRPC 消息本身就是一帧（一个 AU）**（`docs/HOS_SCRCPY_PROTOCOL.md:72-77`），`DecoderPump.onH264Frame(byte[])` 收到什么就整块送解码器（`decode/DecoderPump.java:115-129`、`:188`）。

起始码扫描只用在两个地方，都不参与切帧：

```java
// decode/H264Decoder.java:183-199  hasVclNal：仅用于"这个包该 warn 还是 debug"
static boolean hasVclNal(byte[] data) {
    for (int i = 0; i + 3 < data.length; i++) {
        if (data[i] == 0 && data[i + 1] == 0
                && (data[i + 2] == 1 || (data[i + 2] == 0 && data[i + 3] == 1))) {
            int nalType = data[data[i + 2] == 1 ? i + 3 : i + 4] & 0x1f;
            if (nalType == 1 || nalType == 5) return true;
            i += 4;
        }
    }
    return false;
}
```

`splitAccessUnits` 的分组规则（若 C# 侧要做离线校验，可照搬）：

```java
// decode/H264Decoder.java:285-311（节选）
int auStart = 0;                    // 流首 SPS/PPS/SEI 归入第一个 slice 的 AU
for (...) {
    int nalType = ... & 0x1f;
    if (nalType == 1 || nalType == 5) {           // VCL：一个 slice 起一个新 AU
        if (auStart < i) out.add(Arrays.copyOfRange(data, auStart, i));
        auStart = i;
    }
    i += 4;
}
if (auStart < data.length) out.add(Arrays.copyOfRange(data, auStart, data.length));
```

注意它**保留起始码**（`copyOfRange` 从 NAL 的起始码位置开始），输出仍是 Annex B。

### 3.2 首帧 SPS+PPS 合包怎么处理（全链路最关键的一处）

形态：**第一条 gRPC 消息 ≈ 33 字节，只含 SPS(7)+PPS(8)，不含 slice**。上游的处理是"识别 → 缓存 → 当 extradata 注入 → 绝不送进解码器"。

识别（`decode/H264Decoder.java:318-339`）：

```java
public static boolean isParameterSets(byte[] data) {
    boolean hasParams = false;
    for (...) {
        int nalType = ... & 0x1f;
        if (nalType == 1 || nalType == 5) return false;   // 有 VCL 就不是纯参数集包
        if (nalType == 7 || nalType == 8) hasParams = true;
    }
    return hasParams;
}
```

缓存与注入（`decode/DecoderPump.java:115-129`、`:164-187`）：

```java
// onH264Frame（gRPC 回调线程）
if (H264Decoder.isParameterSets(data)) paramSets = data;   // volatile，跨重连保留
...
// pumpLoop
if (decoder == null) {
    if (paramSets != null) createDecoder(paramSets);        // 参数集一律以 extradata 注入
    else continue;                                         // 首个参数集未到：VCL 帧直接丢弃
}
if (H264Decoder.isParameterSets(chunk)) {
    if (!Arrays.equals(chunk, decoderParams)) {            // 参数集变化（典型：旋转改分辨率）
        DiagnosticRegistry.record(serial, Type.PARAM_SETS_CHANGED, ...);
        closeDecoder(); createDecoder(chunk);              // 旧参数解新帧会花屏，必须重建
    }
    continue;                                              // 重复参数集包直接丢
}
```

注入细节（`decode/H264Decoder.java:99-118`，三个必踩坑）：

```java
byte[] padded = Arrays.copyOf(annexBParams, annexBParams.length + 64); // AV_INPUT_BUFFER_PADDING_SIZE
paramSetsRef = new BytePointer(av_mallocz(padded.length)); // 必须 av_mallocz：avcodec_free_context 会对 extradata av_free
ctx.extradata(paramSetsRef);
ctx.extradata_size(annexBParams.length);
```

- 尾部必须补 **64 个零字节**，否则解码器越界读、实测堆破坏 abort；
- 分配器必须与 `av_free` 配套（`av_mallocz`），用别的分配器在 `avcodec_free_context` 时堆破坏；
- 为什么不用"带内参数集"：帧级多线程下带内参数集向工作线程传播有竞态，紧随其后的 IDR 会 `INVALIDDATA`（`decode/H264Decoder.java:85` 附近 javadoc）。

**重连后的坑**：设备侧 IDR **不内嵌**参数集，重连后可能再也不发参数集 → 上游把 `paramSets` 做成 `volatile` 字段跨 `restart()` 保留（`decode/DecoderPump.java:116-120`、`session/MirrorSession.java:320-341` 的 `pump.restart()` 不清它）。

### 3.3 环形缓冲结构

```java
// decode/H264Decoder.java:69
private static final int RING_SIZE = 4;
// :266-270
rgbaRing = new BytePointer[RING_SIZE];
viewRing = new IntBuffer[RING_SIZE];
dstDataRing = new PointerPointer[RING_SIZE];
dstLinesizeRing = new org.bytedeco.javacpp.IntPointer[RING_SIZE];
// :224

```

- 每槽 `new BytePointer((long)ow*oh*4)`，`asByteBuffer().order(BIG_ENDIAN).asIntBuffer()`，即 **ARGB8888 大端 int**；
- 输出走 `IntBuffer`，每帧 `VideoFrame.pixels()` 返回 `duplicate()`（共享内容、独立 position，**不得长期持有**，`decode/VideoFrame.java:19-24`）；
- 尺寸变化时 `ensureScaler` 把 4 个环**全部置 null 而非释放**（`decode/H264Decoder.java:250-256`）——因为渲染线程可能仍持有旧帧视图，显式释放即 use-after-free；
- `close()` 同样只置 null（`:345-363`），依赖 JavaCPP 的 Cleaner 在无人持有时回收。这正是 v1.0.3 修的闪退根因（见第 7 章 P-02）。

### 3.4 丢帧 / 追帧策略：**不追，直接跳到最新**

三级背压，全部"丢旧"没有"排队等"：

| 层 | 容量 | 满了怎么办 | 定位 |
|---|---|---|---|
| gRPC 回调 → 泵队列 | `QUEUE_CAPACITY = 8` | `pending.poll(); droppedCount++` 再 offer 新帧 | `decode/DecoderPump.java:29`、`:121-128` |
| 泵线程 → 渲染 | 单槽 `AtomicReference<VideoFrame> latest` | 直接覆盖，渲染端永远只拿最新 | `:188-193`、`latestFrame()` |
| 解码线程数 | `thread_count(4)`（帧级并行） | 单线程实测丢帧 2:1，4 线程最坏 +3 帧 ≈50ms 延迟 | `decode/H264Decoder.java:98` |

渲染侧按 `sequence` 单调递增丢弃旧帧（`decode/VideoFrame.java:6-7` 注释），`FrameRenderer` 每帧 `updateBuffer` 覆写 WritableImage（`render/FrameRenderer.java:41-48`）。

### 3.5 如何区分「静态画面无帧」与「真的断流」

判据来自 `session/MirrorSession.java:361-416`，核心是**三条或逻辑 + 一个启动宽限**：

```java
// session/MirrorSession.java:408-416
static boolean shouldReconnectOnSilence(boolean probeAlive, int silentTicks, boolean inputActive) {
    return (inputActive && silentTicks >= 2)   // 有输入注入却连续 2 轮（≈20s）没新帧 → 真死
        || !probeAlive                          // hdc 探活失败 → 设备侧没了
        || silentTicks >= 30;                   // 30 轮 × 10s = 5 分钟兜底
}
```

逐条：

1. **启动宽限**：`decoded == 0 && now - streamStartedAtMs < 30_000` → 只 `requestIDRFrame()` 不判死（`:373-378`），避免刚建流就误杀。
2. **探活**：`probeAlive()` 走**桥内 shell**（不是新起 hdc 进程）执行 `param get const.product.name`，5s 超时（`:419-429`）：
   ```java
   bridge.executeShellCommand("param get const.product.name", 5)
   ```
3. **输入预言机**：`noteInputActivity()` 在每次真实下发控制事件时打时间戳（`control/InputForwarder.java:147`、`session/MirrorSession.java:254-256`），15s 内有过输入视为"活跃用户"，此时 2 轮无帧即判死（`:379-386`）。
4. **5 分钟兜底**：纯静态画面（无输入、探活正常）最多容忍 `PASSIVE_RECONNECT_TICKS = 30` 轮 = 300s（`:62`、`:412`）。

为什么必须要这套：**1.0.20-beta 起设备侧"...IDR 也不再强制推帧"**，静态画面下 `requestIDRFrame` 可能毫无效果，旧的"连续两轮无帧即判死"会每 ~25s 杀一次流（`CHANGELOG.md:10`、`docs/RELEASE_NOTES_v1.0.3.md:12`）。

### 3.6 ≈9 分钟 `UNAVAILABLE` 断连：在哪一层被捕获

**结论：客户端没有捕获 gRPC 状态码这一层代码，它只收到一个 `Throwable`。**

证据：全源码 grep `UNAVAILABLE` → **0 命中**。链路是：

```

  → jar 内部 gRPC onError(StatusRuntimeException: UNAVAILABLE)     【未确认：jar 未反编译】
  → jar 调 ScreenCapCallback.onException(t)
  → HosScrcpyBridge.dispatch "onException"                          stream/HosScrcpyBridge.java:82
  → FrameSink.onStreamError(Throwable)                              stream/FrameSink.java:20
  → DecoderPump.onStreamError：仅 log.warn + errorHandler.accept(t) decode/DecoderPump.java:131-136
  → MirrorSession.onStreamFailure(t)                                session/MirrorSession.java:286-317
  → 指数退避重连（1s,2s,4s,8s,10s，第 6 次起固定 30s）
```

历史背景（`CHANGELOG.md:77-78`、`docs/RELEASE_NOTES_v1.0.0.md`）：v1.0.0 浸泡 2 小时才暴露——"视频流 ~9 分钟被设备侧断开（UNAVAILABLE），客户端无感知、画面冻结"，当时的修法是补断流检测 + 自动重连 + 重连前 `sleep 2s`。

**对 C# 的含义**：既然自己要写 gRPC，就能拿到真正的 `StatusCode.Unavailable`，比上游的"盲 Throwable"更有信息量；但**不能只靠它**——`CHANGELOG.md:60` 明确记录"设备侧退出/被抢占时 gRPC 可能无任何异常回调"，所以 3.5 的三条静默判据必须一起实现。

### 4.5 折叠屏坐标错位（任务书称 issue #4）的具体成因

**先声明可信度**：`reference/` 全仓 grep `折叠|fold|issue|TODO|FIXME` **0 命中**，README 的"已知限制"（`:117-122`）也没写折叠屏。所以**本仓库内没有这个 issue 的文本**，"issue #4"编号与描述 **未确认**。

但从代码结构可以确定这类错位的**必然成因**（`control/CoordinateMapper.java` 全文 66 行）：

1. **单屏假设**：Mapper 只有一个 `deviceWidth/deviceHeight` 对，构造时来自 `hdc.screenSize(sn)` 一次性取值（`session/MirrorSession.java:123-124`），**此后不再更新**。
2. **无 region / 无偏移**：`toDevice` 只有 `scale + offsetX/Y`（居中留边），没有任何"显示区域矩形"概念。折叠屏展开后应用可能只占内屏一部分（分屏/悬浮窗/不同 displayId），或外屏内屏分辨率不同，映射必然系统性偏移。
3. **方向只靠宽高比推**：`horizontal = f.width() > f.height()`（`MirrorSession.java:154`）。折叠屏展开/折叠瞬间画面在"接近方形"的中间态时，宽高比判据会抖动，导致 `displayWidth/displayHeight` 互换错误，坐标成镜像。
4. **分辨率变化只重建解码器，不更新 Mapper**：参数集变化时 `DecoderPump` 重建解码器（`decode/DecoderPump.java:174-186`），但**没有任何代码把新分辨率回写给 CoordinateMapper**。`screenSize` 只在构造时取一次。折叠屏切换内外屏 = 分辨率变化 → 解码器跟上了，坐标映射没跟上。

C# 侧必须补的两件事（上游没有）：① 从每帧实际宽高（或参数集解析出的 SPS 尺寸）刷新 Mapper 的 device 尺寸；② 若支持折叠屏，用 `captureLayout` 的根节点矩形做 region 映射，而不是单纯等比缩放。

| 当前态 | 事件 | 动作 | 目标态 | 定位 |
|---|---|---|---|---|
| IDLE | `start()` 成功 | pump.start → stream.start → renderScheduler.start → startWatchdog | STREAMING | `:204-234` |
| IDLE | `start()` 抛异常 | `state=ERROR` + `pump.close()` + 抛 SessionException | ERROR | `:210-217` |
| STREAMING | `onStreamFailure(t)` | 算退避、排重连任务 | ERROR | `:286-317` |
| ERROR | `reconnect()` 成功 | stream.stop → sleep 2s → pump.restart → stream.start → 计数清零 → startWatchdog | STREAMING | `:320-341` |
| ERROR | `reconnect()` 失败 | 再走 onStreamFailure（继续退避） | ERROR | `:337-341` |
| STREAMING/ERROR | `reconnect()` 被误调 | 直接 return（幂等保护） | 不变 | `:321-323` |
| 任意 | `close()` | 见 5.5 | CLOSED | `:442-460` |

`start()` 有严格前置断言：`if (state != State.IDLE) throw new IllegalStateException("session already started: " + state)`（`:205-207`）。另外 `start()` 在建流过程中会再查一次 `state == CLOSED`，若是则回滚 `stream.stop() + pump.close()`（`:218-228`）——这是"用户在建流期间关窗"的竞态兜底。

### 5.2 看门狗

```java
// session/MirrorSession.java:52-68
WATCHDOG_INTERVAL_MS      = 10_000      // 每 10s 一跳
STARTUP_GRACE_MS          = 30_000      // 启动宽限
INPUT_ACTIVE_WINDOW_MS    = 15_000      // 输入活跃窗口
PASSIVE_RECONNECT_TICKS   = 30          // 30 × 10s = 5 分钟
```

调度（`:343-352`）：`scheduleWithFixedDelay(watchdogTick, 10s, 10s)`，启动时 `watchdogLastDecoded = -1; silentTicks = 0; streamStartedAtMs = now`。

单跳逻辑（`:361-400`）按优先级：

1. 非 STREAMING → 复位计数，返回；
2. `decodedCount` 与上一跳不同 → `silentTicks = 0` + `requestIDRFrame()`，返回；
3. `silentTicks++`；
4. `decodedCount == 0` 且未超 30s 宽限 → 只请求 IDR，返回；
5. `decodedCount == 0` 且超宽限 → 记 `WATCHDOG_STALL("启动宽限 30000ms 内零帧")` → `onStreamFailure(new StreamStalledException())`；
6. 否则算 `inputActive`（15s 内有过输入）、`probeAlive()`、`shouldReconnectOnSilence(...)`；命中则记 `WATCHDOG_STALL("静默判死：探活=… 静默轮=… 有输入=…")` → `onStreamFailure`；
7. 都不命中 → `log.debug("static screen … keep waiting")` + `requestIDRFrame()`（即"静态画面，正常现象"）。

### 5.3 5 分钟静默兜底

`PASSIVE_RECONNECT_TICKS = 30`（`:62`），配 `shouldReconnectOnSilence` 的第三条 `silentTicks >= 30`（`:412`）。含义：**无输入、探活正常、画面确实不动**的情况下，最多容忍 300 秒，之后强制重连一次。这是"宁可白重连一次，也不永久假死"的取舍。

### 5.4 失败重试策略

```java
// session/MirrorSession.java:286-317
int attempt = reconnectAttempts.incrementAndGet();
long delay = attempt <= MAX_RECONNECT_ATTEMPTS          // 5
        ? Math.min(1000L << (attempt - 1), MAX_RECONNECT_DELAY_MS)  // 1s,2s,4s,8s,10s
        : SLOW_RETRY_MS;                                // 第 6 次起固定 30s
```

- **永不放弃**：第 6 次起降频到 30s 一次，一直重试到用户关窗。
- **并发合并**：`if (!reconnectPending.compareAndSet(false, true)) return;`（`:288-291`）——gRPC 错误回调 + 看门狗同时触发只算一次。
- **重连前必须等 2s**：`RECONNECT_SETTLE_MS = 2_000`，注释写明"设备侧 scrcpy 退出需约 2s，重启前必须等，防新旧实例冲突"（`:50`、`reconnect()` 里 `Thread.sleep(RECONNECT_SETTLE_MS)`）。
- **重连后计数器按代清零**：`pump.restart()` 内部清 `sequence`/`decodedCount`/`droppedCount`，`reconnectAttempts.set(0)`；`latest.set(null)` 防渲染旧帧（`decode/DecoderPump.java` restart 段、`CHANGELOG.md:19`）。
- **调度器已关**：`RejectedExecutionException` 静默丢弃并复位 `reconnectPending`（`:309-315`）——关窗后不再重连。

### 5.5 会话生命周期与"防互踢"

- App 层 `serial → MirrorWindow` 单例（`App.java:60-61`、`:147-153`）：同设备再点一次就只 `requestFocus()`，不新建会话——因为**设备侧 scrcpy 是单例**，两条会话会互相踢掉。
- 关窗双保险：`setOnCloseRequest` + `setOnHidden` 都调 `closeSession()`（`ui/MirrorWindow.java:114-118`），注释记录只拦标题栏 ✕ 会漏掉 `stage.close()`，导致僵尸会话无限重连互踢（2026-09-27 卡顿风暴根因）。
- 关闭线程是**非 daemon**（`ui/MirrorWindow.java:439-451`），保证应用退出前把设备侧流停干净。
- `close()` 顺序固定（`session/MirrorSession.java:442-460`）：`state=CLOSED` → SESSION_CLOSED → renderScheduler.stop → watchdogTask.cancel → reconnectScheduler.shutdownNow → stream.stop → pump.close → textInjector.close → controlExecutor.shutdownNow → bridge.close。
- 三个入口互斥：`start` / `reconnect` / `close` 全部 `synchronized`（v1.0.3 收口，`CHANGELOG.md:18`）。

### 6.4 UiStyles.java 为什么只有 695 字节

`ui/UiStyles.java` 全文 26 行，只有一个方法，没有任何样式常量：

```java
// ui/UiStyles.java:13-25
final class UiStyles {
    private UiStyles() { }
    static String dataUrl(String css) {
        return "data:text/css," + URLEncoder.encode(css, UTF_8).replace("+", "%20");
    }
}
```

它只做一件事：把一段 CSS 文本编码成 `data:text/css,` URL，供 `getStylesheets().add(...)` 使用。注释（`:8-10`）解释了为什么必须 `.replace("+", "%20")`：`URLEncoder` 把空格编成 `+`，而 data: URL 里 `+` 是字面量，整条 CSS 会解析失败——样式会**静默丢失**，不报错。

**样式实际散落在 3 个 Java 文件的 3 个文本块里**（没有任何 `.css` 资源文件）：

| 常量/方法 | 位置 | 内容 | 挂载点 |
|---|---|---|---|
| `LIST_CSS` | `ui/MainView.java:52-121` | 设备列表、无线输入框、连接/断开按钮、诊断徽标（`.diag-badge`） | `ui/MainView.java:145` |
| `DIALOG_CSS` | `ui/MainView.java:337-402` | 诊断导出对话框（`.diag-dialog`、单选圆点、默认按钮） | `ui/MainView.java:417` |
| `toolbarCss()` | `ui/MirrorWindow.java:386-431` | 浮动工具条、弹出菜单、关于对话框（`.tool-pill`/`.tool-btn`/`.menu-panel`/`.menu-row`/`.menu-check`/`.about-dialog`） | `ui/MirrorWindow.java:107`、`:373`，封装 `toolbarStylesheetUrl()` 在 `:380-382` |

额外的坑：`Popup` 有独立 Scene，**不继承**主 Scene 的样式表，必须手动复制：

```java
// ui/SideToolbar.java:133
menu.getScene().getStylesheets().setAll(anchor.getScene().getStylesheets());
```

C# 侧的等价做法是把这三段样式集中到一个 `Styles.xaml`（或 `.axaml` Resources），不要再走"内联字符串 + 运行时注入"这条路——上游之所以这样，是因为 JavaFX 单文件分发不想带资源，是历史包袱而非设计优点。

### 8.2 必须改（照搬会出问题）

| 项 | 上游做法 | C# 必须怎么做 | 理由 |
|---|---|---|---|
| **协议实现** | 反射内置 jar | **自己写 .proto + gRPC client**（Grpc.Net.Client，`Http2UnencryptedSupport` 或 `SocketsHttpHandler` 明文 HTTP/2 到 `127.0.0.1:<D>`） | Java 侧零 gRPC 代码可抄（结论 2）；且 Windows 上没有 jar 可用 |
| **设备侧启动** | jar 内部完成，Java 侧空白 | 自己实现：`uitest --version` → 变体选择 → md5 校验 → 推送 → `start-daemon` → `fport` → 连接 → `power-shell wakeup` | §1.1：Java 侧没有任何启动代码可抄，只能照文档逆向结论 |
| **首帧判定** | 依赖 jar 回调 `onReady` | 自己定义：`onStart` stream 建立即算 ready，再靠"首个参数集到达"才算可解码 | 没有 jar 就没有 `onReady` 回调 |
| **解码器** | JavaCPP 绑 FFmpeg 7.1（`avcodec_send_packet` 直用） | .NET 8 可用 `FFmpeg.AutoGen`（同样直接绑 avcodec），**不要**用 `FFmpegMediaSource`/`MediaPlayer` 之类高层封装 | 高层封装会重犯 P-14（`find_stream_info` 阻塞） |
| **环形缓冲所有权** | 依赖 JVM Cleaner 兜底（"永不显式释放"） | 用 `IDisposable` + 引用计数 / `MemoryPool` 显式管理，但**禁止**在渲染线程仍持有帧时释放 | P-02 的根因是生命周期竞态；.NET 没有 GC 保底，必须自己保证"最后一个视图释放后才回收" |
| **坐标映射刷新** | 构造时取一次 `screenSize`，此后不更新 | 每帧或每个参数集变化都刷新 device 尺寸；支持 region（`captureLayout`） | §4.5：折叠屏/旋转分辨率变化的必然缺陷 |
| **长按按键** | 只有成对 `-K -d/-u` | 拆 `keyDown`/`keyUp` 两个命令，中间可控时长 | §4.7 |
| **配置持久化** | `~/.hnscrcpy/config.properties` | `%LOCALAPPDATA%\hnscrcpy\config.json` 之类 Windows 常规位置 | 跨平台路径约定不同；且 .NET 有 `System.Text.Json` |
| **UI 架构** | JavaFX + 内联 CSS data: URL | WPF/WinUI 用 XAML ResourceDictionary | §6.4：内联 CSS 是历史包袱 |
| **gRPC 错误处理** | 只拿 `Throwable`，看不到 StatusCode | 直接判 `StatusCode.Unavailable/Internal`，并保留静默看门狗兜底 | §3.6 |
