## D-01 输入通道采用设备侧 uitest daemon 的 8012 JSON-RPC 长连接

**决定**
控制指令（触摸、滑动、按键、文本输入）不再走 `hdc shell` 逐次调用，改为：
1. 本软件自行在设备上拉起 `uitest start-daemon singleness --extension-name <so>`（不依赖上游是否已起）
2. 自行建立 `hdc fport tcp:<本地空闲端口> tcp:8012`
3. 之后所有输入复用这一条长连接，采用 pipelining（不逐条等响应，靠严格保序配对）

**理由**
实测单次注入延迟：`hdc shell uitest uiInput click` P50 = 412.7 ms；8012 长连接逐条等响应 49.6 ms；pipelining **3.4 ms**。60Hz 触摸流实测零背压（单帧写入 P50 0.07 ms，最大 1.23 ms），响应严格保序。这是「跟手」能否成立的分界线。

**代价**
- 必须自己管理 daemon 生命周期与 fport 的分配/回收；进程退出必须 `fport rm`，否则残留端口。
- 设备上 `kill`（SIGTERM）被拒，停止 daemon 只能 `kill -9`。
- 连接中断要整条重建，不能在原连接上重试。

**被否方案**
- `hdc shell` 逐次调用：412.7 ms，且**常驻 shell 这条路不存在** —— hdc 3.2.0c 不带命令执行直接打印 `Not support stdio TTY mode` 退出，管道接管 stdin 则回 `Unknown operation command...`。即使能常驻，天花板也是约 310 ms/次（uitest 二进制启动就占 260 ms）。
- `hdc shell` 合并批发：320.1 ms，仍不够。

## D-02 0.1.0 只做单指触控，双指缩放推迟到 0.2

**决定**
本版本只实现单指：点按、长按、拖拽（分步 `touchMove`）、滚轮映射为滑动。双指缩放不做。

**理由**
Hypium 的 `Gestures` 是否存在 `pointerIndex` / 多指参数**尚未验证**，盲目排期会把不确定项塞进首个版本。单指已覆盖绝大多数使用场景，双指属于增强。

**代价**
看图片、地图、网页时不能用双指捏合缩放，需退回手机操作。界面上不出现"支持双指"的任何暗示。

**被否方案**
0.1.0 直接做多指：需要先做能力探测，可能卡住整个首个版本。

## D-03 有线模式进 0.1.0，但只做「检测到 USB 就用」

**决定**
`hdc` 对 USB 与无线的命令完全一致，仅设备标识从 `IP:端口` 变为 USB 序列号。0.1.0 的规则只有一条：**枚举设备时若存在 USB 连接的设备，优先使用它**。不为此增加任何设置项、开关或模式选择界面。

**理由**
- 几乎零成本（同一套命令），却能顺带解决三件事：带宽（USB2 480 Mbps vs WiFi 实测约 0.3 Mbps 有效吞吐）可支撑更高帧率与码率；延迟稳定不受无线干扰；顺带充电。
- 不做 UI 复杂度：用户不需要理解"模式"，插上线自动变好即可。

**代价**
插拔线会引起一次会话重建。需在状态栏明确提示当前链路是「USB」还是「无线」，否则用户不知道画质为什么变了。

**被否方案**
做成显式「高性能模式」开关：增加认知负担，收益不明显。

## D-04 画面走 gRPC over `hdc fport`，复用华为闭源组件

**决定**
视频链路：把华为已签名的 `libscrcpy_server_unix_6.8-*.z.so` 推到 `/data/local/tmp`，用 `uitest start-daemon` 加载，`hdc fport` 转发其 gRPC socket，客户端按 Annex B H.264 收流解码。

**理由**
已端到端验证：首帧 794 ms，SPS 解析出 `High@L5.2 / 4:2:0 / 8bit / 1260×2720`，31 个 NAL 与消息数自洽。自研设备侧采集需要写 HAP 装机，且设备 XPM 有签名校验，自研 `.so` 加载不了 —— 这条路走不通。

**代价**
- 依赖华为闭源二进制，无法审计、无法修复其内部缺陷；上游升级变体时客户端可能失配。
- 发布时不能把这 18 MB jar 打进安装包（合规），只能运行时从用户本地环境发现。

**被否方案**
自研 HAP + AVScreenCapture：违反「手机零安装」这条硬约束。

## D-05 音频走蓝牙 A2DP Sink，协议层不做音频

**决定**
PC 侧实现蓝牙 A2DP Sink（把电脑注册成手机的音频输出设备）。视频 gRPC 协议一条音频接口都没有，不在这条链路上做音频。

**理由**
用户要求「电脑出现在手机音频输出列表里，选中后手机不出声」，这**只有 A2DP Sink 能做到**：它把电脑注册成系统级音频设备。内录（AVScreenCapture）只是复制音频，手机照常外放，控制中心不会新增任何项；第三方也无法改别家 App 的音频路由。

**代价**
- 延迟 200~300 ms（SBC），与视频不同源，必须靠缓冲对齐。
- 通话、铃声仍走手机。
- 与 2.4G WiFi 互扰，必须 5GHz。
- 一次只能接管一台手机。

**被否方案**
- HAP 内录：要装机，违反零安装；且无法让手机静音。
- HDMI/DP 采集卡：需要额外硬件，且不能无线。

## D-06 音画同步三档，默认全自动

**决定**
`AvSyncMode { Auto（默认）, ForceSync, ForceLowLatency }`。
- Auto：状态机在 `Interacting / Playing / Idle` 之间切换。输入后 400 ms 内为 Interacting，视频缓冲归零（跟手优先）；音频持续 > 300 ms 且无输入转 Playing，视频缓冲 = 音频延迟 − 视频延迟（默认 250 ms，可调 100~400）。滞回 200 ms，最短停留 500 ms，队列上限 30 帧。
- ForceSync：固定缓冲，音画对齐优先。
- ForceLowLatency：固定零缓冲，操作跟手优先。

**理由**
「跟手」和「音画同步」在物理上互斥：跟手要求不缓冲，同步要求必须缓冲。唯一能同时满足的形态是**按当前活动类型自动切换**，并把选择权留在设置里。

**代价**
自动切换在临界点可能抖动，靠滞回与最短停留时间压制；ForceSync 下拖动窗口会明显感到迟滞。

**被否方案**
只给一种模式：要么永远不跟手，要么永远音画不同步。

## D-07 文件传输：拖入上传、拖出下载

**决定**（需求编号 F-14 / F-15）
- 本地文件拖进镜像窗口 → `hdc file send` 到手机「下载」目录。
- 失败时回退到 `/data/local/tmp/`，并**明确显示实际落点**，不静默失败。
- 传输队列 + 每文件进度 + 可取消。
- 从手机拖出 → `hdc file recv`。

**理由**
`hdc file send/recv` 原生可用，零额外依赖。无线几 MB/s、有线几十 MB/s。

**代价**
大文件需先确认；手机上"下载"目录路径可能因机型而异，需要探测而不是写死。

## D-08 三程序集分层，依赖方向单向

**决定**
```
HdcMirror.App (net8.0-windows)  ← WPF 界面、托盘、生命周期
      ↓
HdcMirror.Decode (net8.0)       ← H.264 解码、帧调度
      ↓
HdcMirror.Core (net8.0)         ← 协议、hdc 封装、输入、音频、配置
```
`Core` 与 `Decode` **禁止引用 WPF 与 Windows 桌面 SDK**。反向依赖一律禁止。

**理由**
解码与协议是纯逻辑，能脱离界面单测（POC 已经证明可以在没有窗口的情况下跑通全链路）。界面改造时不必担心碰坏协议层。

**代价**
界面与逻辑之间需要一层 DTO / 事件，不能图省事直接 `Dispatcher.Invoke` 到 Core 里。跨线程访问必须由 App 层的调度器处理。

## D-09 命名与版本

**决定**
- 正式名 **HdcMirror**，中文名 **鸿蒙手机无线控制**，仓库名 `hdc-mirror`。
- 界面文案仅中文，但**代码里必须预留资源文件**（`.resx` + 强类型资源类），XAML 与 C# 禁止硬编码中文。
- 版本号**唯一来源**为 `Directory.Build.props`，起始 `0.1.0`，各里程碑递增，`1.0.0` 在 M6 之后。

**理由**
名称必须与上游 `hnscrcpy` 区分（本软件不 fork、不共享代码）；版本号单一来源可避免多工程版本漂移（上游就出过这个 bug）。

## D-10 隐私与推送红线

**决定**
- 仓库内不得出现真实设备 IP/端口、设备名与昵称、具体机型与硬件标识、本地用户路径、SSID、手机号、邮箱、令牌、私钥，以及**真实屏幕截图与录屏**。
- 示例地址一律用 RFC 5737 保留地址 `192.0.2.10:5555` 或 `<DEVICE_ADDR>`。
- 源码不得有默认真机地址，设备地址必须由用户提供。
- **任何 `git push` / tag / Release 必须由用户本人明确同意，一次同意只覆盖当次。**

**理由**
用户明确要求：「上传到 GitHub 仓库要经过我的允许」「不允许出现我手机的 IP 端口和设备名称等个人信息」。一旦推送即为公开，改文件不等于移除泄漏。

**代价**
每次推送前必须跑 `tools\pre-push-check.ps1`，三道闸全过（退出码 0）才能去申请许可。

## D-11 不 fork 上游，独立实现

**决定**
不复制、不修改 `taxiao213/hnscrcpy` 的代码。只把它的实现当**参考资料**（已抓取 82 个 java 文件存于 `docs/reference/`，不入库），协议细节以本项目的实测报告为准。

**理由**
以运行行为为准，不以别人的代码为准 —— 实测已经推翻上游文档三处：`payload` 字段号是 3 不是 1、配置帧精确 32 字节不是"约 33"、`uinput -M` 是假成功（返回成功但屏幕无反应）。

**代价**
设备侧启动链（推 so / 起 daemon / fport）必须全部自己写 —— 上游那部分在闭源 jar 里。

## D-12 证据冲突时以最新实测为准，并保留登记

**决定**
技术文档中出现结论冲突时，**以最新一次带原始证据的实测为准**，并在需求说明书附录 C.2「证据冲突登记」中记录双方与裁定理由。

已登记的冲突：
| 冲突 | 两方 | 裁定 |
|---|---|---|
| 触摸注入是否可用 | `03` 号报告称 `uitest uiInput`/`Gestures` 假成功 | `04` 号报告及后续亲测证明**可用** —— 以最新为准 |
| 注入验证方法 | 早期用截图 MD5 比对 | **MD5 不可靠**：状态栏时钟跳动 + JPEG 重编码使哈希恒变，既漏报也误报。必须截图目视或像素差异率比对 |

**理由**
早先的失败根因最终定位为「`module` 字段填了类名而非包名 `com.ohos.devicetest.hypiumApiHelper`」，不是通道本身不可用。若不登记，后来者会照旧结论误判并放弃正确路径。

**代价**
M2 必须内置注入自检（首次连接点一下 + 画面差异比对），失败则降级为只读镜像 + 按键并明确提示，不能假装成功。
