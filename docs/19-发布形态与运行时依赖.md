# 19 · 发布形态与运行时依赖（框架依赖 + 语言裁剪）

> 版本：0.0.9（版本号未改动）　编写日期：2026-11-12
> 本文记录两件事：**① 发布形态从「自包含」改为「框架依赖 + 安装时依赖检测」**、**② 语言资源裁到中文 + 英文并留好扩展位**。
> 所有结论都来自本机实测（Velopack 1.2.161 / .NET SDK 8.0.427），不是推测。

## 一、结论速览

### 1.1 体积对比（同一版本 0.0.9，仅发布形态不同）

| 产物 | 旧：自包含 | 新：框架依赖 | 变化 |
| --- | ---: | ---: | ---: |
| `HdcMirror-win-Setup.exe` | 155.59 MB | **89.43 MB** | −66.16 MB（−42.5%） |
| `HdcMirror-0.0.9-full.nupkg` | 148.42 MB | **82.26 MB** | −66.16 MB（−44.6%） |
| `HdcMirror-0.0.9-delta.nupkg` | 66.28 MB | **0.12 MB** | 见 §1.2 说明 |
| `stage`（publish 输出） | 359.05 MB | **200.75 MB** | −158.30 MB（−44.1%） |
| `HdcMirror-win-Portable.zip` | 148.42 MB | **不再生成** | 所有者要求取消免安装版 |
| 语言资源目录 | 13 个 / 15.51 MB | **1 个（zh-Hans）/ 1.08 MB** | −14.43 MB（自包含基线实测） |

一句话：**每份产物小了 66 MB，其中约 158 MB 是打进包里的 .NET 运行时。**

### 1.2 为什么 delta 从 66.28 MB 掉到 0.12 MB

delta 是「相对上一个版本的差量」，不是「相对自包含的差量」。0.0.1～0.0.8 的 full 包都是 82.2x MB 的框架依赖包，只有 0.0.9 改成了自包含 —— 所以旧 delta 66.28 MB 里绝大部分是**这一版新塞进去的 158 MB 运行时压缩后的体积**；运行时不再进包后，两次发布之间真正变化的只有应用自己的几个 DLL，vpk 日志：

```
[INF] Delta processed 0037 files. 0007 patched, 0030 unchanged, 0000 new, 0000 removed
```

即 37 个文件里只有 7 个变化 ⇒ 0.12 MB。**这正是应用内增量更新最想要的形态**：以后每次发版用户只下几百 KB，而不是几十 MB。

### 1.3 部署实测（本机，.NET 8 已安装）

| 项 | 结果 |
| --- | --- |
| `tools\hotdeploy.ps1`（源码直跑） | 编译 0 错误，robocopy 退出码 3，实例起来，窗口标题「鸿蒙手机无线控制 · HdcMirror」 |
| 静默卸载旧版 | 退出码 0；原装版本是 0.0.8；安装目录 / 快捷方式 / 卸载注册项全部清除 |
| 静默安装新包 `--silent` | 退出码 0，**2.4 秒**完成（不再需要解 158 MB 运行时） |
| 安装目录 | 35 个文件 / 200.57 MB，**运行时文件命中 0 个**（无 coreclr/hostfxr/PresentationFramework） |
| 安装后清单 `current\sq.version` | 含 `<runtimeDependencies>net8-x64-desktop</runtimeDependencies>` |
| 启动 | PID 正常，窗口标题「鸿蒙手机无线控制 · HdcMirror」，工作集 154 MB |
| 用户数据 `%APPDATA%\HdcMirror` | 卸载 + 重装前后都是 5 文件 / 2.85 MB，**未受影响** |

## 二、为什么默认改成框架依赖

`tools\pack\build-release.ps1` 头部注释里写了同样三条，这里展开：

1. **体积**：自包含把 `Microsoft.WindowsDesktop.App` 整份打进包（本机实测 158.3 MB），而用户机器上大概率已经装了 .NET 8 —— 同一份运行时在每台机器上重复存一遍，收益为零。
2. **让 delta 真正有意义**：运行时文件在两次发布之间会产生大量二进制噪声，把 delta 从「几百 KB」抬高到「几十 MB」，应用内增量更新基本失效（见 §1.2）。
3. **运行时该由运行时自己维护**：`.NET 8 桌面运行时` 由微软通过 Windows Update / 官方补丁统一升级。自包含包把运行时钉死在发布时刻，用户拿到的是「装机即开始落后」的运行时，安全补丁要等我们重新发版才到位。

代价与兜底：

- 用户机器上**没有** .NET 8 桌面运行时 ⇒ 装不上。这条已经由 Velopack 自带的依赖检测 + 我们附带的安装前检查脚本覆盖（§三～§六）。
- 万一依赖检测方案在某个环境下不可用，`build-release.ps1` 保留逃生开关：

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File tools\pack\build-release.ps1 -SelfContained
```

`-SelfContained` 时脚本会 `--self-contained true`，并**自动忽略** `-Framework`（包内自带运行时，再声明依赖只会让 Setup 白装一遍运行时），只打一段告警。

## 三、Velopack 1.2.161 的依赖声明机制（实测）

### 3.1 声明入口

`vpk pack --framework net8-x64-desktop`，打包日志直接确认：

```
[INF] Runtime Dependency: net8-x64-desktop
```

运行时 id 语法是 `net<主版本>-<架构>-<profile>`，profile 为 `desktop` 表示 `Microsoft.WindowsDesktop.App`（另有 `-runtime`、`-aspnet`、`-sdk` 等，属于 Velopack 支持的其它运行时族）。

### 3.2 这个声明写到哪了

| 文件 | 是否含运行时依赖 |
| --- | --- |
| `dist\releases.win.json` | **不含**。只有 `PackageId / Version / Type / FileName / SHA1 / SHA256 / Size` |
| `dist\assets.win.json` | **不含**，同上 |
| `Setup.exe` 内嵌包清单 | **含**，Setup 读它做检测 |
| 安装后 `%LOCALAPPDATA%\HdcMirror\current\sq.version` | **含**：`<runtimeDependencies>net8-x64-desktop</runtimeDependencies>` |

所以：**更新通道的元数据里看不到依赖声明，依赖检测发生在 Setup（安装时），不发生在应用内更新时。** 这是正常设计 —— 应用内更新时运行时早已存在，否则程序根本起不来。

### 3.3 Setup 到底怎么检测

Setup.exe 内嵌了运行时探测模块（二进制里可见源码路径 `src\bins\src\windows\runtimes.rs`、`prerequisite.rs`），判定依据是 `%ProgramFiles%\dotnet\shared\<FrameworkName>\<版本>` 与注册表里的运行时安装记录，缺失时日志原文形如：

```
[INFO] Package Runtime Dependencies: net7-x64-desktop
[INFO] Checking application pre-requisites...
[INFO]     .NET 7.0.0 X64 WindowsDesktop is missing.
[INFO] Downloading 1 missing pre-requisites...
```

已安装时：

```
[INFO]     .NET 8.0.0 X64 WindowsDesktop is already installed.
```

> 上面两段是**真机跑出来的**：为了让「缺失」分支真的触发，我们用一个**一次性探针包**做了对照实验 —— 同一份 stage、同一个 packId，只把 `--framework` 改成 `net7-x64-desktop`（本机装的是 6.0.36 / 8.0.33 / 9.0.22 / 10.0.14，唯独没有 7.x）。把该安装器的下载出口指向死代理，让它「检测到缺失 → 尝试下载 → 立刻失败」，从而只观察检测与下载的判定，不往系统里装任何东西。对照日志留存在 `tools\pack\probe-log-hdcprobe-net7.out.txt`、`probe-log-hdcprobe-net8.out.txt`。

## 四、缺运行时时，用户到底看到什么

### 4.1 交互双击 `Setup.exe`（默认路径）

Setup.exe 内建 40 多种语言的本地化，**含简体中文**。与依赖相关的中文文案（二进制内取出的原文，逐字）：

| 内部 key | 简体中文原文 |
| --- | --- |
| `missing-deps-header` | `需要其他组件` |
| `missing-deps-body` | `{ $app_title } 需要先安装以下组件: { $deps }。是否立即下载并安装它们?` |
| `deps-download-header` | `正在下载所需组件` |
| `deps-download-body` | `正在下载 { $dep_name }，请稍候...` |
| `restart-header` | `需要重新启动` |
| `restart-body` | `在继续安装之前需要重新启动计算机。请重新启动计算机后再次运行安装程序。` |
| 控制台拒绝分支 | `Cancelling setup. Pre-requisites not installed.` |

- `{ $app_title }` 渲染为 `HdcMirror`；`{ $deps }` / `{ $dep_name }` 渲染为**运行时 id 本身**，即用户看到的是 `net8-x64-desktop` 而不是「.NET 8 桌面运行时」这种人类可读名字 —— 这是 Velopack 目前的粗糙点，所以 §六 的检查脚本才有存在价值。
- 用户点「是」→ 直接进入「正在下载所需组件」，进度条走完自动静默安装运行时。
- 用户点「否」→ 安装中止，提示 pre-requisites not installed。
- **装完运行时不需要重新双击 Setup**：`missing-deps → deps-download → apply` 在同一串步骤里连续执行，运行时装好后同一次安装会接着往下走。
- 唯一需要重跑的情况：运行时安装器返回「需要重启」时，Setup 会把 `restart-body` 那段话显示出来 —— 此时才需要重启机器并重新双击安装。

### 4.2 运行时是从哪下的（不是官方下载页）

Setup 内置的是**自动下载 + 静默安装**，不是打开浏览器让用户点下载。二进制里可读到的地址与流程：

1. 版本发现：`https://dotnetcli.blob.core.windows.net/dotnet` 下的 `.../latest.version`（按 channel + 架构取当前最新补丁版本号）
2. 下载基址：`https://builds.dotnet.microsoft.com/dotnet`
3. 下载路径模板：`/WindowsDesktop/windowsdesktop-runtime-{ver}-win-{arch}.exe`（另有 `/Runtime/dotnet-runtime-`、`/aspnetcore/Runtime/aspnetcore-runtime-`、`/dotnet-sdk-` 等族）
4. 安装参数：`/install /silent`（静默）/ 回退 `--passive /norestart /q`

**结论：Velopack 给出的不是 `https://dotnet.microsoft.com/download/dotnet/8.0` 那个网页，而是微软官方的 CDN 直链，自动下、自动装、不需要用户去网页点。** 这比「打开网页让用户自己找」体验更好，但它隐含两件事需要知情：

- 安装过程会从 `builds.dotnet.microsoft.com` / `dotnetcli.blob.core.windows.net` 拉 55 MB 左右的运行时安装包 ⇒ **目标机必须能上外网**。内网/离线环境要靠 §六 的检查脚本手动装。
- 下载失败时 Setup 直接报网络错误并中止（实测缺依赖 + 死代理 ⇒ `Network error: Http error: io: ... (os error 10061)`），不会静默跳过。

### 4.3 静默安装（`--silent`）的行为差别

`--silent` 隐藏所有对话框并自动回答提示，因此**缺依赖时它不会问，直接开始下载安装运行时**；下载/安装失败则整个安装以非 0 退出码终止。批量部署时要注意：`--silent` 的机器必须能访问上述 CDN。

## 五、我们的兜底层：`HdcMirror-安装前检查.cmd`

所有者要求「安装时检测、缺什么明确告诉用户、可以点下载、装完继续安装」。Velopack 自带的检测能满足「检测 + 自动下载」，但它的提示里出现的是 `net8-x64-desktop` 这种 id，且下载失败只有一个英文网络错误。所以在 `vpk pack` 之后，打包脚本会额外把一份中文自检脚本放进 `dist`：

- 源文件：`tools\pack\preinstall-check\HdcMirror-安装前检查.cmd`
- 打包脚本第 ⑤b 步自动复制到 `dist\HdcMirror-安装前检查.cmd`（编码 GBK/936，保证 PowerShell 之外的 `cmd` 也正常显示中文）
- 用户拿到 `dist` 后**先双击它，再双击 `Setup.exe`**

### 5.1 检测逻辑（三条依据，任一条命中即认为已安装）

```bat
dir /b /ad "%ProgramFiles%\dotnet\shared\Microsoft.WindowsDesktop.App\8.*"
dotnet --list-runtimes | findstr /C:"Microsoft.WindowsDesktop.App 8."
reg query "HKLM\SOFTWARE\Microsoft\Windows\CurrentVersion\Uninstall" /f "Windows Desktop Runtime - 8." /d
reg query "HKLM\SOFTWARE\WOW6432Node\Microsoft\Windows\CurrentVersion\Uninstall" /f "Windows Desktop Runtime - 8." /d
```

用三条而不是一条，是因为：运行时装在 x64 与 x86 两套目录、`dotnet` 可能不在 PATH、注册表 `Uninstall` 键在两个视图下都可能有记录。任一条命中就判「已安装」，避免误报。

### 5.2 缺失分支说什么

```
[缺少] 未检测到 .NET 8 桌面运行时（Microsoft.WindowsDesktop.App 8.x）
       本程序是「框架依赖」发布，必须先装运行时才能启动。
       注意：必须是 .NET 8 的 Desktop Runtime（桌面运行时），
             装 ASP.NET Core Runtime 或 .NET Runtime 都不行。

       官方下载页：https://dotnet.microsoft.com/download/dotnet/8.0
                   （选「.NET Desktop Runtime 8.x」→ x64）
```

按回车会用 `start` 打开这个官方下载页；用户装完后回到窗口按任意键，脚本 `goto :check` **原地重检**，通过则显示检测到的版本号，并询问是否直接启动同目录下的 `HdcMirror-win-Setup.exe`。

### 5.3 为什么检测不能塞进应用启动路径

框架依赖的应用在缺少运行时的情况下**根本加载不起来**（CLR 都起不来，主程序第一行代码永远不会执行）。所以检测必须发生在 `Setup.exe` 之前，或者由 Setup 自己完成 —— 这也是本方案选择「独立 .cmd 前置 + Velopack 自带检测」而不是「应用启动时自检」的唯一原因。

### 5.4 自测开关

脚本支持 `HDCMIRROR_CHECK_SIMULATE_MISSING=1` 环境变量强制走缺失分支（不打开浏览器、不等待按键），便于在已装运行时的机器上验证文案。两条分支均已实测通过；本机检测到的版本为 `8.0.33`。

## 六、打包脚本改了什么（`tools\pack\build-release.ps1`）

| 项 | 改后 |
| --- | --- |
| 默认发布形态 | 框架依赖：`dotnet publish --self-contained false` |
| 运行时声明 | `vpk pack --framework net8-x64-desktop`（由 `-Framework` 控制，默认值即此） |

## 七、界面语言（已实现运行时切换）

### 7.1 现状

| 项 | 事实 |
| --- | --- |
| 文案唯一来源 | `src\HdcMirror.App\Resources\Resources.resx`（中性资源，简体中文） |
| 键数量 | **262 个**，无重复 |
| 强类型访问器 | `src\HdcMirror.App\Resources\Strings.cs`，全部走 `ResourceManagerInstance.GetString(key, CultureInfo.CurrentUICulture)` |
| 英文本体 | `src\HdcMirror.App\Resources\Resources.en.resx`，与中性 resx **262 键逐一对应、键序一致** |
| 产物 | `en\HdcMirror.resources.dll`，25 088 字节；中文留在主程序集（317 952 字节）里 |
| XAML 取值方式 | `{x:Static res:Strings.Xxx}` 共 128 处，**静态求值**：窗口加载时一次性取，之后不会变 |

键集合一致性由脚本核对：键集 / 键序 / 占位符（`{0}` `{1}` `{0:N1}`）/ 换行数 / `·` 分隔符 逐项 diff，任何一项不为 0 就不许提交。改 resx 后重跑一遍即可。

因为 `{x:Static}` 是静态求值，**热切语言不现实**（会留下半中半英），所以本功能的设计前提是：**切换语言 = 重启一次进程**。

### 7.2 切换机制

1. 配置在 `%APPDATA%\HdcMirror\settings.json`：
   - `UiLanguage`：`""` = 跟随系统 / `"zh-Hans"` / `"en"`
   - `LanguageChosen`：是否已经问过用户（显式布尔，不靠「文件是否存在」推断）
2. `App.OnStartup` 的**第一件事**（早于任何窗口与资源字典构建）：`Localization.Apply(AppSettings.Current.UiLanguage)`，内部设 `CultureInfo.DefaultThreadCurrentUICulture` 与 `CultureInfo.CurrentUICulture`。
   **只动 UICulture，不动 CurrentCulture** —— 数字、日期、单位仍跟系统走，FFmpeg 参数拼装与日志解析不受影响。
3. **首次启动**（`LanguageChosen == false` 且 `UiLanguage` 为空）弹 `src\HdcMirror.App\Views\LanguageDialog.xaml`：420×260、居中、不可缩放，标题故意双语（「选择界面语言 / Choose your language」），两个大按钮，默认高亮跟随系统 UI 语言。选完 → 写 `UiLanguage` + `LanguageChosen = true` + `Save()` → `Localization.Apply(...)` → 继续启动。**这一步不重启**，因为主窗口还没建。
4. **设置 → 通用设置 → 界面语言**改选后：立即 `Save()`，然后 `App.RequestLanguageRestart()` —— 释放单实例 Mutex 与激活用 `EventWaitHandle` → 带命令行参数 `--after-language-change` 启动新实例 → 旧实例 `Shutdown()`。
   新实例的 `TryAcquireSingleInstance` 在 **5 秒内每 200 ms 重试（最多 25 次）**，所以不会出现「提示已有实例在运行、实际什么都没起来」的假死。

### 7.3 资源裁剪（`SatelliteResourceLanguages`）

`src\Directory.Build.props`（**该文件带 UTF-8 BOM，改动时必须保留 `EF BB BF`**）：

```xml
<SatelliteResourceLanguages>zh-Hans;en</SatelliteResourceLanguages>
```

中性资源语言是 `zh-CN`（`<NeutralResourcesLanguage>zh-CN</NeutralResourcesLanguage>`），因此**中文编进主程序集、英文才是卫星资源** —— 磁盘上看到的是 `en\` 目录，不是 `zh-Hans\`。这是正确的，不是配错。

历史数据：改前自包含包曾带 13 个语言目录、合计 15.51 MB（cs de es fr it ja ko pl pt-BR ru tr zh-Hans zh-Hant，每个目录 17 个卫星程序集）；裁到 `zh-Hans;en` 后框架依赖形态下语言目录只剩 `en` 一个（25 KB）。即：语言裁剪「额外」省下的 14.43 MB 已经包含在 158.3 MB 的运行时缩减里，这个开关现在的真实价值是**防止以后误加回一堆语言**，以及在需要回退自包含时仍然省 14.43 MB。

### 7.4 Velopack Setup 的界面语言

安装器（`Setup.exe`，Velopack）自己的界面语言**由 Velopack 按系统区域决定，不受本功能影响**：它既不读我们的 `settings.json`，也不看进程的 `CurrentUICulture`。

所以「安装向导是中文、装完打开应用是英文」是正常组合，不是 bug。

## 八、新增一种语言：三步

1. **复制** `src\HdcMirror.App\Resources\Resources.en.resx` 为 `Resources.<culture>.resx`（例如 `Resources.ja.resx`，`<culture>` 用 BCP-47 名如 `ja` / `zh-Hant` / `pt-BR`）。逐键翻译 value，**key 一个都不能增删改** —— 缺 key 会回落到中文，表现为半中半外。
2. **`src\Directory.Build.props` 的 `SatelliteResourceLanguages` 追加**：`zh-Hans;en` → `zh-Hans;en;ja`。这一步不做，第 1 步的 resx 会被裁掉，等于白做。
3. **编译验证**：`C:\dotnet8\dotnet.exe build src\HdcMirror.App\HdcMirror.App.csproj -c Debug`，输出目录应出现 `ja\HdcMirror.resources.dll`（约 +25 KB）。

配套改动（新语言要能在界面上选到）：

- `src\HdcMirror.App\Services\Localization.cs`：把新 culture 加进常量与 `Resolve()` 的白名单（现在只接受 `""` / `zh-Hans` / `en`）。
- `src\HdcMirror.App\Views\SettingsPage.xaml`：语言 `ComboBox` 加一项 `Tag="ja"`，文案用新键 `Lang_Japanese`（中英两个 resx 都要加）。
- 不需要动 `<NeutralResourcesLanguage>`：中文永远是兜底。
- 不需要动 `tools\pack\build-release.ps1`：语言集合由 props 决定。

验收清单（每加一种语言都跑一遍）：

```
1. 两个 resx 键集合 diff 为空（键集/键序/占位符/换行/·）
2. 编译 0 警告 0 错误，输出目录出现 <culture>\HdcMirror.resources.dll
3. 设置在设置页切到该语言 → 自动重启 → 主窗口 + 四个设置页无中文残留
4. tools\selftest.ps1 9 项通过、tools\privacy-scan.ps1 退出码 0
```

## 十、已知注意点

1. **vpk 会对主程序入口打印一条告警**：`VelopackApp.Run() was found in method 'System.Void HdcMirror.App.App::OnStartup(...)'`，建议把 `VelopackApp.Build().Run()` 移到 `Main()` 第一行。不属本次改动范围（涉及 `.cs`），仅记录。
2. **`--silent` 安装必须有外网**：缺运行时它不会询问，直接去 `builds.dotnet.microsoft.com` 下载；内网部署请先离线装好 .NET 8 桌面运行时，或用 `HdcMirror-安装前检查.cmd` 引导。
3. **不要改 `src\Directory.Build.props` 的 `<Version>`**：版本号是唯一来源，打包脚本从它读取，改它等于改发布版本。
4. **`--noPortable` 是硬约定**：所有者明确不做免安装版，脚本第 ⑥ 步会因残留 `*-Portable.zip` 直接失败，不要为了「先看一眼」把它注掉。
5. 依赖检测证据留存：`tools\pack\probe-log-hdcprobe-net7.out.txt`（缺失分支实测日志）、`probe-log-hdcprobe-net8.out.txt`（已安装分支）、`probe-log-hdcprobe-net7.err.txt`（下载被阻断时的报错原文）。
