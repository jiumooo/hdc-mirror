## 二、选型：为什么最终是 FFmpeg，而不是 Media Foundation

### 2.1 首选方案（Media Foundation）曾经完整实现，但被实测否决

M1b 第一版按任务书首选实现的是 Windows 自带 `CLSID_CMSH264DecoderMFT` 的 COM 互操作（`[ComImport]` + `PreserveSig`，vtable 逐槽手写，`MFStartup(0x00020070)`）。过程中修掉了两个真正的坑：

1. **.NET 8 不会把 COM 基接口的槽位排在派生接口之前**。`interface IMfSample : IMfAttributes` 这种继承声明会让 `IMfSample` 的所有方法落到 `IMFAttributes` 的槽位上（症状：`MFCreateSample` 之后 `AddBuffer` 返回 `0xC00D36E6`＝`MF_E_ATTRIBUTENOTFOUND`，`SetSampleTime` 直接 `AccessViolationException`）。改为**扁平声明**（把 30 个 `IMFAttributes` 方法在每个派生接口里原样重复）后全部正常。
2. **`ProcessOutput` 的数组参数默认按 SAFEARRAY 封送**，会抛 `0x80131165 Typelib export: Type library is not registered`。加 `[MarshalAs(UnmanagedType.LPArray, SizeParamIndex = 1)]` 后正常。

修完之后，`SetInputType` / `SetOutputType` 全部 `S_OK`，输出类型也正确协商成 `NV12 1260×2720`（后续 STREAM_CHANGE 后为宏块对齐的 `1264×2720`），但**一帧都不输出**。系统性取证（5 种封装组合 × 多轮变体，含 Annex B / AVCC / 有无序列头 / 关键帧 SYNC_POINT / 独立样本 / 端到端 DRAIN）：

- 每个 AU 都是 `ProcessInput = 0x0`、`GetInputStatus = 1`（接受数据）、`GetOutputStatus = 0`、`ProcessOutput` 恒 `0xC00D6D72`（`MF_E_TRANSFORM_NEED_MORE_INPUT`）；
- 只有发完 `MFT_MESSAGE_NOTIFY_END_OF_STREAM` + `COMMAND_DRAIN` 之后才吐出 7 帧，且此时才报 `MF_E_TRANSFORM_STREAM_CHANGE`；
- 换成 ffmpeg 用标准 x264 编码的 640×480 流，同一 MFT **同样是流式阶段 0 帧**；
- 同一份真机码流用 ffmpeg 解码 `29/29` 帧正常，证明码流本身合法。

结论：MS H.264 解码器 MFT 在**流式阶段**拒绝出帧，与样本封装、时间戳、几何、缓冲区大小都无关（`MFCreateMemoryBuffer(6876160)` 也没被拒），没有可控的修复点。MF 实现已完整归档到 `_probe/mfarchive/`，不进入交付代码。

### 2.2 备选方案（FFmpeg.AutoGen）一次跑通

- NuGet：`FFmpeg.AutoGen 9.0.1.1` + `FFmpeg.AutoGen.Bindings.DynamicallyLoaded 9.0.1.1`（包版本即生成时的 FFmpeg 版本）；

- 首次验证即 **29/29 帧**，`AV_PIX_FMT_YUV420P → BGRA`，首帧 12.9 ms，全部 115 ms。

## 三、线程模型

```
┌─────────────────────────────── 后台线程 A：帧泵 + 解码（Task.Run，MTA）──────────────────────────────┐
│  ScrcpyClient.ReadFramesAsync（IAsyncEnumerable）                                                    │
│        │  ScrcpyFrame{AnnexB, IsKeyFrame, Pts, Flags}                                               │
│        ├─ Extradata（32 B SPS+PPS）与上次不同 → FfmpegH264Decoder.Configure()                        │
│        └─ FfmpegH264Decoder.TryDecode(annexB, pts)                                                   │
│                  avcodec_send_packet → avcodec_receive_frame →（若配置帧变过，先拼回 SPS/PPS 再送）    │
│                  sws_scale：YUV420P → BGRA32（写入复用缓冲，末尾多留 4 KB 保护带）                     │
│        └─ FrameExchange.Publish(pixels, w, h, stride)   ← 只保留最新一帧，UI 落后即丢                 │
└──────────────────────────────────────────────────────────────────────────────────────────────────────┘
                                             │ 互斥锁（拷贝一次即释放）
┌─────────────────────────────── UI 线程：DispatcherTimer（16 ms / Render）─────────────────────────────┐
│  FrameExchange.Consume → WriteableBitmap.WritePixels（尺寸变化时才重建位图）                          │
│  状态栏：Status_Mirror_Streaming（尺寸 + 每秒重算的 fps）/ Status_Mirror_Idle（≥1.5 s 无新帧）          │
└──────────────────────────────────────────────────────────────────────────────────────────────────────┘
```

- **解码绝不在 UI 线程**，UI 线程每帧只做一次 `WritePixels`（固定位图、固定缓冲，无 per-frame 分配，无 `new Bitmap`）。
- **背压策略是「丢旧帧」而不是「排队」**：`FrameExchange` 只保存最新一帧，解码快于上屏时旧帧直接作废，延迟不累积。
- 解码器与 gRPC 流都在同一条后台流水线上串行执行，`sws` 上下文与像素缓冲天然无竞争。
- 零帧**不触发任何动作**：没有看门狗、没有超时重连；`MillisecondsSinceLastFrame` 只用于状态栏文案。

## 四、每帧数据通路

```
设备 H.264 编码器
   │  (仅在画面变化时推送)
   ▼
上游 daemon（`uitest start-daemon ... -p 5000`，socket: scrcpy_grpc_socket）
   │  hdc fport tcp:15000 → localabstract:scrcpy_grpc_socket
   ▼
ScrcpyClient（gRPC 双向流）
   │  ReplyMessage.payload(field 3) → ParamValue.valBytes(field 5)，flags/pts/len 为 field 1 varint
   ├─ 首条精确 32 B 配置帧 → 截留为 Extradata（不产帧）
   └─ 后续 Annex B 访问单元（flags & 2 = 关键帧）
   ▼
FfmpegH264Decoder.TryDecode
   │  配置帧变化时把 32 B SPS+PPS 前置拼回访问单元（运行期更新，不重建解码器）
   ▼
sws_scale（YUV420P → BGRA32，BT.709，解码器线程内完成）
   ▼
FrameExchange（单槽双缓冲，跨线程只留最新一帧）
   ▼
WriteableBitmap.WritePixels（UI 线程，Bgra32，stride = width × 4）
   ▼
PhoneFrame（圆角 26 px 黑底容器，按真实帧宽高比等比缩放居中）
```

## 五、真机实测数据

采集环境：`My Phone`（`HarmonyOS NEXT 真机（型号略）`，`192.0.2.10:5555`，无线连接），主机 i5-14600KF（14C/20T）、31.8 GB 内存、RTX 3060 Ti、Windows 10.0.26300。

### 5.1 帧率：设备侧推流 ≈ 请求帧率的一半

| 设备侧参数 | 激励 | 帧数 / 时长 | 均值 fps | 峰值（1 s 窗口） | 单帧解码均值 |
| --- | --- | --- | --- | --- | --- |
| `-frameRate 30 -bitRate 8388608` | 无（锁屏动态壁纸） | 303 帧 / 20 s | **15.2** | 18.0 | 3.90 ms |
| `-frameRate 60 -bitRate 16777216` | 无 | 629 帧 / 20 s | **31.4** | 39.0 | 4.65 ms |
| `-frameRate 60 -bitRate 8388608` | 无（竖屏 1260×2720） | 189 帧 / 6 s | **31.5** | 37.0 | 3.73 ms |
| `-frameRate 60 -bitRate 16777216` | 连续滑动 | 247 帧 / 8 s | 30.9 | 38.0 | 4.95 ms |
| `-frameRate 30 -bitRate 8388608` | 6 秒慢拖 | 63 帧 / 8 s | 7.9 | — | — |

- 传 30 只推 15.2 fps、传 60 推 31.4 fps，与码率无关（30 档实际只有 1.06 Mbps，远低于上限）⇒ **产品默认请求 60 fps**（`MirrorSession.CaptureFrameRate = 60`），否则拿不到 ≥25 fps。
- `uitest uiInput swipe ... <duration>` 只注入起止两点，长 duration 反而几乎不产生连续运动，不能用它压帧率。

### 5.2 单帧解码耗时分布（含 YUV420P→BGRA32 转换）

| 场景 | min | 中位 | p95 | max | 均值 |
| --- | --- | --- | --- | --- | --- |
| 真机 2720×1260（60 fps 档，1089 帧） | 2.52 ms | **3.31 ms** | 4.57 ms | 62.61 ms | **3.73 ms** |
| 真机 1260×2720（竖屏档） | 2.52 ms | 3.31 ms | 4.57 ms | 62.61 ms | 3.73 ms |
| 离线 29 帧（samples 抓包） | 2.76 ms | 3.14 ms | 5.65 ms | 61.75 ms | 5.31 ms |

纯解码吞吐上限 ≈ **268 fps**（单线程），远高于设备推流上限，所以本机不是瓶颈；`max` 62 ms 的尖峰来自首帧与配置帧切换后的首个 IDR。

### 5.3 首帧与 CPU

| 指标 | 实测 |
| --- | --- |
| 探针首帧（画面在动） | 517 ms / 568 ms / 607 ms / 636 ms |
| 探针首帧（画面已暂停、只能等设备下一次推送） | 1183 ms |
| App 冷启动首帧（含设备枚举 + daemon 启动 + fport） | 1792 ms（暖机）/ 4096 ms（冷启，含 LAN 扫描） |

### 5.4 画面与设备一致性

用 `hdc shell snapshot_display` 抓设备当前帧（2720×1260 与 1260×2720 两种朝向都抓过）与镜像窗口截图逐张比对：内容一致（同一集短视频、同一条字幕、同一进度点），圆角容器内**无变形**——`RenderFrame` 在首帧到达时用真实帧尺寸校正宽高比（`_phoneAspect`），横竖屏自动适配。

## 六、零帧与断流：实测与处理

| 场景 | 观测 | 结论 |
| --- | --- | --- |
| 画面暂停（静止） | 6 秒窗口 **2 帧**、10 秒窗口 **5 帧**（播放按钮呼吸动画），`连接存活 = True`，累计解码失败 **0** | 零帧不误判断流 |
| 同上，动一下手机 | 恢复出帧 **1370 ms** | 零帧后能立刻恢复 |
| 完全静止约 80 秒 | 设备侧主动结束推送：`ScrcpyStreamException: 服务端结束了视频流且没有收到 onEnd 回应` | 这是**设备行为**，与零帧判定无关 |
| 熄屏（`keyEvent 26`） | 10 秒 0 帧，但连接直接断（`存活 = False`） | 熄屏是**流终止**，不能当作零帧证据 |
| 断流后的恢复 | 有界自动重连（最多 5 次，间隔 2 s），每次重连重建 fport/daemon 与解码器 | 见下 |

## 九、遗留问题

1. **原生库体积**：`native/ffmpeg/win64` 共 183.9 MB（`avcodec-63` 单个就 114.9 MB），不入库、构建时只复制。若后续要做安装包，需要裁剪（只保留 h264 解码 + swscale，或用静态链接的精简构建）。
2. **GPL 传染性**：BtbN 的 `gpl-shared` 构建含 GPL 组件。若产品要闭源分发，需换成 `lgpl-shared` 构建并同步 `native/ffmpeg/win64/SOURCE.txt` 与许可声明。
3. **设备推流上限**：请求 60 fps 实测只有 31.4 fps，是设备侧抓取/编码能力决定，产品无法再往上提；若后续需要更顺滑，只能等设备侧接口暴露更高档位。
4. **长时间完全静止会被设备关流**（约 80 秒），目前已用有界重连兜住（5 次 × 2 s）；重连期间画面会短暂停住（实测 5 秒内恢复），后续可考虑静默预热保活。
5. **横竖屏切换**会触发配置帧变化与分辨率切换（1260×2720 ↔ 2720×1260），解码器支持运行期更新、画面自动重排，但切换瞬间有 1~2 帧的尺寸抖动。
6. **`crash-*.log` 噪音**：gRPC 传输层在服务端异常关流时会抛出未被观察的 `Task` 异常，崩溃守卫已 `SetObserved()` 并记录，不影响进程，但会在日志目录留下 `crash-*.log`。属于 Grpc.Net 内部行为，不影响镜像功能。

---

## 十、明确的里程碑边界

- **Miracast 无关**：本里程碑走的是 hdc + 上游 daemon 的 gRPC H.264 帧流，与 Miracast（Wi-Fi Display）投屏协议没有任何关系，不涉及 WFD 会话、P2P 组网或系统级投屏。
- **音频未涉及**：只处理视频访问单元；`ReplyMessage` 的音频 payload、`swresample`、音频播放链路一律未实现，原生库里 `swresample-7` 只是依赖闭包的一部分，未被调用。
- **输入未涉及**：产品侧没有任何注入通道（不发送触摸/按键）。实测中出现的 `uitest uiInput ...` 只存在于 `_probe/` 下的验收工具里，用于制造画面变化，不进入产品代码。
