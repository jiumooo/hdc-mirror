# M1a 交付说明 —— 协议层

> 版本：0.1.0（Directory.Build.props 唯一来源）
> 范围：只做协议层。不含解码、渲染、输入注入、蓝牙音频、界面、Velopack、多设备持久化。
> 设备地址一律用占位符 `<DEVICE_ADDR>` / `192.0.2.10:5555`；真机地址只存在于测试命令行参数。

- **判活只认** `cat /proc/net/unix | grep scrcpy_grpc_socket`。设备上原有 daemon 可能没带 `--extension-name`，只服务自己的 socket，不能当作本链路可用。
- **停止只走 `kill -9`**：设备侧拒绝 SIGTERM。
- 启动命令固定为 `cd <远端目录> && uitest start-daemon singleness --extension-name <文件名> -scale … -frameRate … -bitRate … -p … -iFrameInterval … &`；`cd` 必须有，`--extension-name` 只给文件名不给绝对路径。
- 幂等：先 `stat -c %s` 比对远端大小，一致就不推送。
- **变体选择不按 uitest 版本号匹配**（实测 uitest 7.0.0.1 直接可用 6.8 变体）：从 jar 的 `libscrcpy/` 条目里筛 `.z.so`、排除 `emulator`，按「`ServerEntry` 精确命中 > 内核版本等于 `PreferredKernelVersion` > 含 `_unix_` > 版本降序 > 文件名」排序，逐个尝试，成功即记 `LoadedVariant`；失败时把本次起的进程 kill 掉再试下一条。
- 设备端文件名 `libscreen_casting_<版本键>.z.so`，**不覆盖上游已有的 `libscreen_casting.z.so`**。
- 只清理自己推送的文件，且 `rm` 之后回读 `ls` 确认。

### 3.1 六轮调试留下的四条实测事实（都已写进代码注释）

| 观测 | 结论 |
|---|---|
| `onStart` 后配置帧**立刻**到达，随后长时间零帧 | 配置帧（flags=8）是建流即发；视频帧只在画面变化时产生 |
| 只发 `onRequestIDRFrame`、不造画面变化：6 次全部 `result=0`，仍然零帧 | daemon 接受请求，但没有新画面就不编码；IDR 请求不等于强制出图 |
| 造画面变化（滑动）后：帧按段涌出 | 「按屏幕变化推流」确证；首帧延迟必须在这个前提下测，否则测到的是「等画面变化」的时间（第一次实测 7331 ms 就是纯等待） |
| 第 3 轮把 IDR 请求与滑动串在一起：第二组「配置帧 + IDR」之后服务端主动关闭流（收流中断） | 高频请求 IDR 会打断流；M1b 只在建流/重建后调一次 |

## 4 与 POC 数字的对比

| 指标 | 本轮实测 | POC 报告 | 判定 |
|---|---|---|---|
| 首帧耗时 | **547 ms** | 794 ms（另一次 1695 ms） | 同量级，更快 |
| 消息条数 | 30 | 30 | 一致 |
| 视频字节 | 269,707 B | 272,102 B | 差 0.9%，同量级 |

| flags 分布 | `flags=0`:28、`flags=2`:1 | 配置帧 `flags=8`、首个 IDR `flags=2`、其余 `flags=0` | 一致（配置帧被截留，不计入帧） |
| 配置帧长度 | 32 字节 | 32 字节（SPS 23 + PPS 9） | 精确一致 |
| SPS | `High L5.2 4:2:0 8bit 1260x2720`，profile_idc=100、level_idc=52、chroma=1、bit_depth=8、frame_mbs_only=true | 同 | 逐项一致 |
| 使用变体 | `libscrcpy/libscrcpy_server_unix_6.8-20260801.z.so`（247,989 B） | 同一条 | 一致 |
| 端口 | `tcp:15000` → `localabstract:scrcpy_grpc_socket` | 同 | 一致 |

**帧长 min 的口径差异**：POC 的统计把 32 字节配置帧也算进帧长（所以 min=32）；本实现把配置帧截留为 extradata、不产出 `ScrcpyFrame`，因此 min 是真实视频帧的最小值（5,804）。两边 max 都在 3 万字节量级，是同一套编码参数（`-bitRate 8388608 -frameRate 30 -iFrameInterval 2000`）下的 IDR。

- 本次推送的 `libscreen_casting_6.8.z.so` 已删除，`ls` 回读确认无残留。

## 7 遗留问题与 M1b（解码器接入）需要注意的点

1. **零帧是正常现象，不是故障。** 设备只在画面变化时推流，静置时一帧没有。M1b 的播放器不要用「固定时间内无帧」判死；判活只能靠 `scrcpy_grpc_socket` 是否监听，或 gRPC 是否抛错。
2. **不要高频调用 `onRequestIDRFrame`。** 第 3 轮实测里，IDR 请求与画面变化交替触发时，第二组「配置帧 + IDR」后服务端会主动关闭流。建议只在建流成功、以及断流重建后各调一次。
3. **配置帧可能重复下发。** 每次请求 IDR 都会再跟一帧 `flags=8`。`ScrcpyClient` 目前是覆盖式写入 `Extradata`（可接受），但 **M1b 的解码器必须支持运行期更新 SPS/PPS 并重建解码器配置**。当前没有对外事件，M1b 需要时再加 `ConfigurationChanged`。
4. **9 分钟 UNAVAILABLE 未实测。** 本轮最长单次收流约 20 秒，断线路径只在代码层成立（异常包装 + 明确抛出）。M1b 做长跑时补一次实测证据，并把重连策略写进文档。
5. **`ScrcpyFrame` 不含配置帧**，所以帧长统计与 POC 报告口径不同（见 §4）。M1b 落盘裸码流时要把 `Extradata` 单独写一次，否则文件不可解。
6. **`pts` 是纳秒、单调递增**，本轮未做统计（M1a 不要求）。M1b 做音画同步时以它为准，并注意设备侧约 9 分钟重建一次会不会把 pts 归零（未验证）。
7. **复用既有 daemon 的路径**：socket 已在监听时 `EnsureRunningAsync` 直接复用且 `StartedByUs=false`，此时 `ProcessId=-1`、`RemoteServerPath=null`，`CleanupAsync` 不会杀别人的进程也不会删别人的 so。M1b 上线遇到「复用了上游 daemon」时，`fport` 远端仍是 `localabstract:scrcpy_grpc_socket`，无需特殊处理。
8. **hdc 路径的「设置项」目前由 `HdcRunner` 构造参数承载**，`AppSettings` 还没有对应字段，等 M2 接界面时再加（不属 M1a 范围，避免提前改 M0 的 settings 契约）。
9. **隐私扫描仍有 3 处命中**（`docs/07`、`docs/08`、`src/HdcMirror.App/Resources/Resources.resx`），全部是脚本把一句普通中文（连词 + 动词 + 设备名词，语义上跟具体的人无关）判成「人名 + 设备词」组合，属规则误报；未使用 `-Fix`（会把正常中文改成 `My Phone`）。新增的 Core 代码零命中。是否收紧该脚本是独立议题。
10. **不打包 jar。** `ScrcpyDaemon` 只从调用方给的 `JarPath` 里取 so，仓库与产物都不含 18 MB 的 jar（D-04/D-10）。
