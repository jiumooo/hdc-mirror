## 1. hdc 命令矩阵

hdc 路径：`%USERPROFILE%\.hnscrcpy\tools\windows-x64\hdc.exe`（Ver 3.2.0c）

### 1.1 list targets

```
$ hdc list targets
192.0.2.10:5555

$ hdc list targets -v
192.0.2.10:5555		TCP	Connected	localhost	hdc
COM1		UART	Ready	unknown...	hdc
COM5		UART	Ready	unknown...	hdc
```

**结论**：可用。`-v` 输出 **5 列**（`目标 连接类型 状态 主机名 服务名`，制表符分隔）。无线目标显示 `TCP / Connected`；本机 COM1/COM5 是 UART 桩，**不是真实设备，代码里要过滤掉**。

### 1.2 tconn

```
$ hdc tconn
[Fail]CreateConnect failed

$ hdc tconn 192.0.2.10:5555
Connect OK

$ hdc tconn -h
（空输出——hdc 子命令无帮助文本）
```

**结论**：必须带 `ip:port` 参数，无参直接失败。`-h` 不提供帮助（**所有 hdc 子命令都无 `-h`**，`fport` 无参还报 `[Fail]Unknown command`）。

### 1.3 shell

```
$ hdc shell "echo RECOVERED_OK"
RECOVERED_OK
```

**⚠️ 关键缺陷：`hdc shell` 不传播退出码。**

```
$ hdc shell "echo rc_test; exit 7"
rc_test
$ echo $LASTEXITCODE
0
```

**对 C# 客户端的含义**：不能靠进程退出码判断设备侧命令成败，**必须解析 stdout 内容**（例如约定打印哨兵串）。

**其它壳层缺陷**：
- `/bin/sh` 是精简 busybox/musl 环境，**没有 `awk`**：`/bin/sh: awk: inaccessible or not found`
- 没有 `wm`：`/bin/sh: wm: inaccessible or not found`

### 1.4 file send / file recv

```
$ hdc file send probe.txt /data/local/tmp/probe.txt
FileTransfer finish, Size:58, File count = 1, time:14ms rate:4.14kB/s

$ hdc file recv /data/local/tmp/probe.txt probe_back.txt
FileTransfer finish, Size:58, File count = 1, time:11ms rate:5.27kB/s
```

**受限点**：读 `/system/bin/*` 会被拒。

```
$ hdc file recv /system/bin/uitest uitest.bin
[Fail]Error opening file: permission denied
```

**绕法（已验证）**：先 shell 内 `cat` 转存到 tmp，再 recv。

```
$ hdc shell "cat /system/bin/uitest > /data/local/tmp/uitest_copy.bin"
$ hdc file recv /data/local/tmp/uitest_copy.bin uitest.bin
（962112 字节，md5 0f638ad50d480e6e07f0c1629a36cf14）
```

### 1.5 fport / fport ls

```
$ hdc fport
[Fail]Unknown command...          ← 无参不打印用法

$ hdc fport tcp:15000 localabstract:scrcpy_grpc_socket
Forwardport result:OK

$ hdc fport ls
192.0.2.10:5555    tcp:15000 localabstract:scrcpy_grpc_socket    [Forward]
192.0.2.10:5555    tcp:16000 localabstract:uitest_socket    [Forward]
192.0.2.10:5555    tcp:36987 tcp:8012    [Forward]

$ hdc fport rm tcp:15000 localabstract:scrcpy_grpc_socket
Remove forward ruler success, ruler:tcp:15000 localabstract:scrcpy_grpc_socket
```

**幂等性**：同一条规则重复建立**返回 OK 不报冲突**。设备侧 socket 不存在时也会 accept，随后立刻 EOF（**连接成功不等于服务在**）。

**删除语法坑**：必须给**完整的两个端点**，只给本地端口会失败：

```
$ hdc fport rm tcp:15000 tcp:15000
[Fail]Remove forward ruler failed, ruler is not exist tcp:15000 tcp:15000
```

### 1.6 kill

```
$ hdc kill
Kill server finish

$ hdc list targets
[Empty]                ← 设备连接全断
```

**⚠️ 这是最危险的一条**：`hdc kill` 杀的是 **hdc server**，会

1. 断开所有设备连接（`list targets` → `[Empty]`）
2. **清空全部 fport 规则**（包括别人的）

**恢复流程（已验证）**：

```
$ hdc start
（无输出）

$ hdc tconn 192.0.2.10:5555
Connect OK

$ hdc list targets -v
192.0.2.10:5555		TCP	Connected	localhost	hdc
```

**C# 客户端要求**：自己 kill server 后必须 `tconn` 重连并**重建全部 fport**；更稳妥的做法是**根本不调 kill**。

### 1.7 hdc 命令矩阵总表

| 命令 | 可用 | 关键参数 / 输出 | 坑 |
|---|---|---|---|
| `list targets` | ✅ | `[-v]` 5 列 | `-v` 含 COM1/COM5 假设备 |
| `tconn` | ✅ | `<ip:port>` → `Connect OK` | 无参失败，无 `-h` |
| `shell` | ✅ | `"<cmd>"` | **不传退出码**；无 awk / 无 wm |
| `file send` | ✅ | `<local> <remote>` → `FileTransfer finish...` | 写系统目录被拒 |
| `file recv` | ✅ | `<remote> <local>` | 读 `/system/bin` 被拒，需 `cat` 中转 |
| `fport` | ✅ | `tcp:L localabstract:S` → `Forwardport result:OK` | 幂等；无帮助 |
| `fport ls` | ✅ | 3 列规则 | — |
| `fport rm` | ✅ | 必须**两端点都给** | 只给端口报 `ruler is not exist` |
| `kill` | ✅ | `Kill server finish` | **断连 + 清空全部 fport** |

## 3. 手动拉起投屏服务

### 3.1 命令与参数

```bash
cd /data/local/tmp && \
/system/bin/uitest start-daemon singleness \
  --extension-name libscreen_casting.z.so \
  -scale 1 -frameRate 30 -bitRate 8388608 \
  -p 5000 -iFrameInterval 2000 &
```

| 参数 | 含义 | 实测取值 |
|---|---|---|
| `start-daemon singleness` | 启动 uitest 守护进程（单实例模式） | 固定 |
| `--extension-name <文件名>` | 加载的扩展 so。**必须是文件名，不能给绝对路径**，且**必须先 cd 到 so 所在目录** | `libscreen_casting.z.so` |
| `-scale` | 缩放比 | `1` |
| `-frameRate` | 帧率上限 | `30` |
| `-bitRate` | 码率（bps） | `8388608`（8 Mbps） |
| `-p` | 端口 | `5000`（**实测不监听任何 TCP，见下**） |
| `-iFrameInterval` | IDR 帧间隔（ms） | `2000` |

参数名常量来自 jar 反编译 `HosRemoteConfig`：` -scale ` ` -frameRate ` ` -bitRate ` ` -iFrameInterval ` ` -virtual_keyboard_height `。

### 3.2 如何判定启动成功

**⇒ 上游走的是「虚拟屏 + MakeMirror 镜像」路线，不是直接抓物理屏。**


### 3.4 纯 uitest 服务端（不带 extension）

```bash
cd /data/local/tmp && /system/bin/uitest start-daemon singleness > /data/local/tmp/daemon.log 2>&1 &
```

| 启动方式 | 提供的能力 | 监听 |

## 4. fport 端口策略

### 4.1 `localabstract:scrcpy_grpc_socket` 可用

```bash
$ hdc fport tcp:15000 localabstract:scrcpy_grpc_socket
Forwardport result:OK

$ hdc fport ls
192.0.2.10:5555    tcp:15000 localabstract:scrcpy_grpc_socket    [Forward]
```

连上后 gRPC 完全可用（见 §5.1）。

### 4.2 旧版 `tcp:5000` 是否需要

**不需要。** 实测依据：

1. daemon 启动带 `-p 5000`，但 `/proc/net/tcp` 里 **5000 不处于 LISTEN**
2. 设备 `uitest --version` = **7.0.0.1**，远高于 jar 反编译出的版本阈值 `6.0.2.1`
3. jar 内 `HosRemoteConfig` 的兜底分支 `'/system/bin/uitest start-daemon singleness --extension-name %s -p 5000 &'` 只在低版本走

**C# 客户端**：`uitest >= 6.0.2.1` 一律用 `localabstract:scrcpy_grpc_socket`。

### 4.3 端口被占用时怎么换

`hdc fport` 本地端口由客户端指定，**换一个本地端口即可**，设备侧端点不变：

```bash
hdc fport tcp:15001 localabstract:scrcpy_grpc_socket     # 换本地端口重试
```

**实测行为**：
- 同一规则重复建立 → 返回 `OK`（**幂等，不报冲突**）
- **设备侧 socket 不存在时也会 accept**，随后立刻 EOF ⇒ **"fport 成功"不能证明服务在**，必须在应用层做一次握手
- 移除必须给完整两端点（§1.5）

**建议策略**：本地端口用「探测可用 → 绑定 → 失败换下一个」的循环，范围取 15000–15100。

### 4.4 设备侧 8012 端口（额外发现，强烈建议用）

`/proc/net/tcp` 实测：

```
6: 00000000:1F4C 00000000:0000 0A ... uid=2000    ← 8012 LISTEN，属 shell
```

`0x1F4C = 8012`，**由 `uitest start-daemon singleness` 打开**。上游正是把它 fport 出来用：

```
192.0.2.10:5555    tcp:36987 tcp:8012    [Forward]
```

实测 `127.0.0.1:36987` 完全可用：

| 请求形态 | 响应 |
|---|---|
| 裸 JSON + `\n` | `{"result":null,"exception":"Invalid request, incorrect module/method/params value"}`（83 字节） |
| `HEAD + 8字节长度 + JSON + TAIL` | `{"result":{"displayId":0,"x":1260,"y":2720}}`（44 字节，**裸 JSON，无包裹**） |

**⇒ 8012 通道比抽象 socket 更省事：请求可带帧也可裸发，响应一律裸 JSON。**

## 5. uitest Gestures JSON-RPC

### 5.1 视频侧 gRPC（顺带跑通，作为基线）

proto（从 jar 的 `scrcpy.proto` 反编译，proto3、**无 package**）：

```protobuf
service ScrcpyService {
  rpc onStart(Empty) returns (stream ReplyMessage);
  rpc onEnd(Empty) returns (ReplyEndMessage);
  rpc onRequestIDRFrame(Empty) returns (ReplyEndMessage);
}
message ReplyMessage { string data = 1; int32 reply_type = 2; map<string, ParamValue> payload = 3; }
message ParamValue { oneof val { int64 val_int=1; double val_double=2; string val_string=3; bool val_bool=4; bytes val_bytes=5; float val_float=6; } }
message ReplyEndMessage { int32 result = 1; }
message Empty {}
```

- 路径 `/ScrcpyService/onStart`，头 `content-type: application/grpc` + `te: trailers`，body = gRPC 帧 `\x00\x00\x00\x00\x00`
- 响应头：`:status=200`、`content-type: application/grpc`、`grpc-accept-encoding: identity, deflate, gzip`
- **视频字节在 `payload["data"].val_bytes`，不是 `ReplyMessage.data`（field 1 永远为空）**
- payload 固定四键：`data`(bytes) / `len`(int) / `pts`(int，毫秒) / `flags`(int)
- `flags`：**8 = 配置帧（SPS+PPS），2 = 关键帧（IDR），0 = 普通帧**
- **按需推流**：静置 20 秒只收到 3 条消息，第 0 条 `t=2136ms len=32 nal=[7,8] flags=8`，第 1 条 `t=2158ms len=39512 nal=[5] flags=2` ⇒ **首帧延迟 2136ms，画面不变就不发帧**
- 码流是 Annex B H.264：`00 00 00 01 67 64 00 34`（High profile, level 5.2）、`00 00 00 01 68 ee 33 c8`（PPS）

### 5.2 JSON-RPC 帧格式（决定性发现）

**设备 8012 / 抽象 socket 的帧结构**：

```
_uitestkit_rpc_message_head_  (28 字节 ASCII)
+ 8 字节大端无符号整数 = 后续 JSON 字节数
+ JSON UTF-8
+ _uitestkit_rpc_message_tail_  (28 字节 ASCII)
```

**响应**：**裸 JSON，无 head/tail 包裹**（44–198295 字节不等）。

**核心：`module` 的值是包名，不是类名！**

```json
{"module":"com.ohos.devicetest.hypiumApiHelper",
 "method":"callHypiumApi",
```

### 5.5 高频 move 的节流阈值（实测）

| 调用 | n | 耗时 | 吞吐 | p50 | p95 | max | 失败 |
|---|---|---|---|---|---|---|---|
| `triggerKey(1)` | 200 | 28.63s | **7.0/s** | 141.5ms | 160.8ms | 186.7ms | **0** |
| `getDisplaySize` | 200 | 11.66s | **17.2/s** | 58.1ms | 72.2ms | 108.4ms | **0** |

## 8. 坐标基准

### 8.1 屏幕真实分辨率怎么取

**`wm` 命令不存在**：

```
$ hdc shell "wm size"
/bin/sh: wm: inaccessible or not found
```

**唯一可用来源是 JSON-RPC**：

```json
Driver.getDisplaySize    → {"displayId":0,"x":1260,"y":2720}
Driver.getDisplayDensity → {"displayId":0,"x":4095,"y":8840}
```

**语义澄清**：
- `getDisplaySize` 的 `x/y` = **像素分辨率 1260 × 2720**
- `getDisplayDensity` 的 `x/y` = **4095 × 8840**，这不是分辨率，是 **dpi 相关值**（约 3.25 倍），**不要拿它当坐标系**
- `captureLayout` 根节点 `bounds:"[0,0][1260,2720]"` 与 `getDisplaySize` **完全一致** ⇒ 坐标单位就是**物理像素**

**hidumper 交叉验证**：

```
$ hdc shell "hidumper -s RenderService -a screen"
screen[0] ... 1260x2720 ... screenType=EXTERNAL_TYPE ... activeMode 120Hz
支持刷新率 120 / 90 / 60 / 30
```

### 8.2 坐标原点

**左上角 `(0,0)`，右下角 `(1259,2719)`**，单位物理像素。依据：`captureLayout` 根 `bounds="[0,0][1260,2720]"`，且点击 (180,2112) 落在 dock 栏图标范围内（`bounds=[122,2086][239,2139]` 的"设置"文字）。

**bounds 格式**：`[left,top][right,bottom]`（**右/下是开区间**）。中心点 = `((l+r)/2, (t+b)/2)`。

### 8.3 折叠屏内外屏

**本机不是折叠屏**：`HarmonyOS NEXT 真机（型号略）` 是 直板机型。`getDisplaySize` 只返回 `displayId:0` 一个屏。

**`displayId` 的实测行为**：
- `Driver.getDisplaySize` 返回 `displayId:0`
- `captureLayout` 的 attributes 里 `displayId` 字段为**空字符串**
- 投屏 daemon 建的是虚拟屏 `{id: 4294967295, associatedScreenId: 0, w*h: [1260*2720], screenType: VIRTUAL_TYPE_SCREEN}`，`associatedScreenId` 指向物理屏 0

**⇒ 折叠屏需在真机上另测，本条不可测（无折叠设备）。** 但给出了可用的判定路径：`getDisplaySize` 返回的 `displayId` 数量与数值。

## 9. 稳定性

### 9.1 连续注入能撑多久

| 通道 | 连续次数 | 失败 | 结论 |
|---|---|---|---|
| 按键 `triggerKey(1)` | 200 | **0** | 28.63 秒内无一次失败，进程未死 |
| 只读 `getDisplaySize` | 200 | **0** | 11.66 秒零失败 |
| `Gestures touchMove` | 300 | **0** | 18.30 秒零失败 |
| 单次截图 `uitest screenCap` | 17+ | 0 | 每次都成功（除锁屏后） |

**⇒ 在本轮测试量级（数百次连续调用）内没有断开。** 未做到让连接自然断开。

### 9.2 断在哪一层

**没有观测到断开**，但明确了**三层各自的失败模式**：

| 层 | 失败信号 | 实测是否出现 |
|---|---|---|
| TCP 连接层 | `WinError 10061 积极拒绝` / `10054 强迫关闭` | 出现过（hdc kill 之后、daemon 死后） |
| JSON-RPC 应用层 | `{"exception":{...}}` 或 `SessionDeath3!` | `SessionDeath3!` **每次请求都有**（设计如此） |
| 注入执行层 | hilog 无 `Inject touchEvent` / 有 `29201` | **触摸必现** |

**关键坑：`SessionDeath3!` 不是故障。** 每处理一个请求就新建并销毁一个 session，200 次请求 = 200 条 `SessionDeath3!`。**拿它当错误会误判。**

### 9.3 靠什么信号能提前发现

按可靠性排序：

1. **`Driver.getDisplaySize` 探活**（~58ms，最便宜）：返回结构变了就说明 daemon 换代
2. **`captureLayout` 根节点 bounds**：拿不到或 bounds 变了 = UI 层异常
3. **hilog 里的 `29201` 计数**：只用于判定**触摸**是否被拒，**不能用于判定连接健康**
4. **`hilog -x | grep 'A03100/uitest'`**：`SessionDeath3!` 属正常；`Check condition ... failed` 才是真错误
5. **不要用** `uitest uiInput` 的返回码、`hdc shell` 的退出码 —— 两者都不可信

**建议的客户端健康检查**：每 2 秒发一次 `getDisplaySize`，连续 3 次超时（>1s）即判定 daemon 死，触发 `ps -ef | grep singleness` 复核并重启。

- **归因不唯一**：本次测试期间上游 hnscrcpy 一直在拉 8Mbps 级别的 H.264 流，**长尾更可能来自上游占带宽 + 设备省电策略**，不能全算在蓝牙头上
- **未做「关蓝牙」对照实验**：AGENTS.md 第十二节禁止改动本机系统设置（网卡/系统配置），因此**没有主动开关蓝牙适配器**。本项只能给出「蓝牙开启状态下的基线」，无法给出「开关前后对比」

**⇒ 第 10 项判定：部分可测。** 基线已给出（p50=5ms / p95=158ms / 0 丢包），但**因果关系未确证**。若要做对照，需要在操作者同意下临时禁用蓝牙适配器再测一轮。

## 12. 给 C# 客户端的结论：能做 / 不能做

### 12.1 可以实现的

| 功能 | 依据 |
|---|---|
| 视频投屏 | gRPC `ScrcpyService.onStart` 流式 H.264，Annex B，按需推流 |
| 请求关键帧 | `onRequestIDRFrame` |
| 读屏幕尺寸/方向/密度 | `Driver.getDisplaySize` / `getDisplayRotation` / `getDisplayDensity` |
| 读完整 UI 树（控件级） | `Captures.captureLayout`，116–198 KB JSON，含 bounds/text/type/bundleName |
| 返回桌面 / 返回键 | `Driver.pressHome` / `pressBack` |
| 发送任意键码 | `Driver.triggerKey [keyCode]` / `[keyCode, keyAction]` |
| 通过 fport 自定义端口 | 本地端口可任意换，设备端 `localabstract:scrcpy_grpc_socket` 或 `tcp:8012` |

### 12.2 做不到的（**这是 C# 客户端的功能边界**）

| 功能 | 原因 | 依据 |
|---|---|---|
| **触摸点按/滑动/拖动** | shell 无 MMI 注入权限，`29201 operation not permitted`，**静默失败** | §5.4 |
| **鼠标事件注入** | 同 MMI 路径 | §5.2/5.4 |
| **`uitest uiInput` 任何命令** | 同上，且**返回码伪造**（`No Error` 但无效果） | §6.3 |
| **无 root 下的真实输入注入** | 需要 `ohos.permission.INJECT_INPUT_EVENT` 或系统签名 | 29201 |
| **锁屏状态截屏** | `Failed to get display pixelMap` | §11.5 |
| **`Driver.wakeUpDisplay` 真正唤醒** | 返回成功但无效果 | §6.2 |
| **`Driver.setDisplayRotation` 真正旋转** | 返回成功但 `getDisplayRotation` 不变 | §7.3 |
| **靠 `hdc shell` 退出码判成败** | hdc 不传播退出码 | §1.3 |

### 12.3 对产品形态的影响

**触摸注入不可用 ⇒ 当前「手机镜像 + 鼠标控制」的产品形态在无 root 的 HarmonyOS NEXT 上无法完整实现。**

可选的三条路：

1. **只读镜像 + 键盘映射**：视频 + 按键可用，触摸不行。适合「演示/投屏/看板」场景
2. **改用 AAMS 语义操作**：`pressHome` / `pressBack` / `triggerKey` 可用，配合 `captureLayout` 做「按控件名点击」——但最终仍需触摸注入才有点击动作，**此路不通**
3. **申请系统签名或 `INJECT_INPUT_EVENT` 权限**：超出本项目范围，需华为生态合作

**建议**：先按「方案 1」交付可用版本，把触摸控制标为「需要提权，待定」。

## 附录 B：本次测试踩过的工具坑

1. **PowerShell 会吃掉 `-c "...json..."` 里的双引号** ⇒ 一律用独立 .py 文件或 `@file` 传 JSON
2. **PowerShell here-string `@'…'@` 里的 `"` 仍会被处理坏** ⇒ 脚本内只用单引号
3. **PowerShell 跑含中文的 .ps1 会用 GBK 解析导致乱码** ⇒ 脚本只用 ASCII，路径用 `$PSScriptRoot`
4. **`Start-Job` 里跑 h2 客户端会 0 帧** ⇒ 改前台跑即通
5. **`javap_lite.py` 解析 field 必须读全 `access+name+desc+attr_count+attrs`**，少读会 struct.error
6. **手机侧没有 `awk`** ⇒ 进程查询用 `grep -v grep` 而不是 `awk '{print $2}'`
7. **`hdc file recv /system/bin/*` 被拒** ⇒ 先 shell 内 `cat` 转存到 `/data/local/tmp`
