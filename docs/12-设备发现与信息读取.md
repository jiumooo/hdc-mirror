## 3. 交付 A：局域网设备发现

### 3.1 hdc 自身有没有发现能力（实测，四条路）

| 候选路径 | 实测结果 | 结论 |
| --- | --- | --- |
| `hdc discover` | 存在（`help verbose`：*Discover devices listening on TCP via LAN broadcast*）；**固定 6.1 s 返回**，连跑 3 次 6 110 / 6 091 / 6 107 ms，输出恒为 `[Info]Please add HDC server's firewall ruler to allow udp incoming, udpport:8710` + `[Info]Broadcast find daemon, total:0` | 保留，但**不能当唯一手段** |
| UDP 8710 手工广播 | 自发 `OHOS.HDC.DISCOVER` 到 `255.255.255.255:8710`，只收到一个来自**本机另一个网卡**的回声（自己发的包回环），设备无应答 | 手机不应答裸广播；实现里必须过滤本机地址 |
| mDNS | `_hdc._tcp.local`、`_hwadb._tcp.local`、`_adb-tls-connect._tcp.local`、`_hdc-tls-connect._tcp.local` 四类查询**全部 0 应答**；连 `_services._dns-sd._udp.local` 也 0 应答（本机 mDNS 环境本身不可用） | 放弃，不实现 |
| `hdc list targets -v` | 只列**已连接**设备，且夹杂 `COM1`/`COM5`（UART Ready）干扰项 | 只能覆盖"已连接"，不能当发现 |

补充两条决定设计的实测：

- **ICMP 不可用**：`Ping.Send(设备地址, 800)` 两次均 `TimedOut`（282 / 494 ms）。手机不回 ping，主机存活只能靠 TCP。
- **闭端口被丢包不是 RST**：设备只开了无线调试那一个 TCP 端口（连接 ~51 ms 成功），
  其余端口（5555 / 8012 / 8710 / 36987 / 12345 / 5037 / 8080）**全部 ~400 ms 超时**。
  因此「全 /24 × 65535 端口」要 3 亿次 400 ms 等待，物理上不可行 → 默认只探固定端口，深度扫描必须点名主机。

### 3.2 最终方案：四层 + 一次权威验证

```
① hdc list targets                     → 已连接无线设备（IsConnected = true，USB 不混入）
② hdc discover（与 ③ 并行启动）         → 广播发现的 ip:port（本机实测恒为空，保留以备防火墙放开）
③ 本机每个网卡的 /24 × CandidatePorts  → TCP 探测（SemaphoreSlim 限流，300 ms 超时）
   └ 端点判定：连接失败=Closed / 立刻 EOF=ClosedByPeer / 非 hdc banner=Banner / 静默或带 HW magic=候选
④ hdc tconn <ep> / -remove             → 权威验证：连不上的剔除；连得上但扫描前没连的，验证后立刻断开还原
⑤（可选）DeepScan                       → 只对点名主机按 2048 端口窗口深扫，命中即停
```

为什么要第 ④ 层：光靠「端口开着 + 对端静默」仍会误报。实测对比：

| 端点 | 连上后 400 ms 内的行为 | 只有 ③ 的判断 | 加 ④ 之后 |
| --- | --- | --- | --- |
| 真机无线调试端口 | 静默（连接保持，不主动发 banner） | 候选 ✅ | `tconn` 190 ms 返回 `[Info]Target is connected, repeat operation` → 保留 |
| 网关上的 8710 | **读到 0 字节，立刻 EOF** | 被 `ClosedByPeer` 剔除 | — |
| 网关上的 5555 | 同上 | 被 `ClosedByPeer` 剔除 | — |
| 局域网内两台静默服务 5555 | 静默（与真机行为相同） | **误报为候选** ❌ | `tconn` 424 / 429 ms 返回 `[Fail]Connect failed`（exit 仍是 0，只能按内容判）→ 剔除 |

所以 `VerifyWithTconn` **默认开启**。它带来的副作用只有：验证期间真机会被连上约 0.2 s，
随后自动 `tconn <endpoint> -remove` 断开，`list targets` 回到验证前状态（§3.6 有实测）。

| `DeepScan` | `false` | 丢包网络下单机 65535 端口需数分钟 |
| `DeepScanHosts` | 空 | 未点名时取 `KnownEndpoints` 的地址；`DeepScan` 开着但无主机则直接跳过并记 Warn |
| `ProgressIntervalMilliseconds` | 1 000 | 心跳间隔，满足「不许 >2 s 无输出」 |

### 3.4 进度与取消

- `ScanAsync` 内部用 `PeriodicTimer` 起一条心跳，**每 1 000 ms 必推一次进度**，
  即使某阶段完全没进展（例如在等 6.1 s 的 `hdc discover`）界面也不会断流。
- 每次 TCP 探测前 `state.SetDetail(ip)`，所以进度里能看到正在扫哪台机器。
- 取消：所有探测都用同一个 `CancellationToken`；`Task.WhenAll` 之后补一次 `ThrowIfCancellationRequested()`，
  保证取消时能被上层 `catch (OperationCanceledException)` 捕获，而不是静默返回半截结果。
- 扫描结束（含异常/取消路径）在 `finally` 里推 `Completed` 并记 Info 级耗时，日志一条不多一条不少。

### 3.6 「已连接」与「仅发现」的区分（实测）

为了验证第二档，做了一次可控实验：断开当前连接 → 用 `KnownEndpoints` 只指向这台设备扫描 → 立即重连。

```
① 断开连接（hdc tconn <设备地址> -remove）
② list targets = [[Empty],]                      ← 设备确实"在线但未连接"
③ known-endpoint 模式扫描：
     扫描结束：候选 1 个（已连接 0 个），耗时 12815 ms
     设备地址        connected=False             ← 报成「仅发现」，正确
④ 扫描后 list targets = [[Empty],]                ← 验证时建立的临时连接已被 -remove 清掉
⑤ 重连（hdc tconn <设备地址>）
⑥ 恢复后 list targets = [<设备地址>]              ← 现场还原
```

同一次实验里，`hdc tconn <设备>` 对**已连接**设备返回 `[Info]Target is connected, repeat operation`（190 ms），
对**非 hdc 端口**返回 `[Fail]Connect failed`（424 / 429 ms），两者 exit code 都是 0 ——
所以 `ConnectAsync` 的返回值只能按输出内容判（含 `fail` / `error` 即失败），不能看 exit code。

### 4.6 容错策略

| 层 | 做法 |
| --- | --- |
| 超时 | ctor 默认 **3 s**，`<=0` 抛 `ArgumentOutOfRangeException`；每条命令一个 linked CTS + `CancelAfter`，超时只 Warn，该字段留空 |
| 异常 | `HdcException`（含 `HdcCommandException`）与超时一律吞掉并记 Warn，`ReadAsync` 不抛（只有用户取消才抛 `OperationCanceledException`） |
| **按内容判错** | 设备命令失败也可能 exit 0（`param get` 失败就是 exit 0 + `fail! errNum`），所以除 exit code 外还查 `Permission denied` / `fail!` / `inaccessible or not found` / `No such file or directory` / `not found` / `no closing quote` |
| 缺项 | `HdcDeviceInfo.MissingFields` 列出没读到的字段，`IsComplete` 一次判断，界面可据此只标灰不报错 |
| 降级链 | `Name`：`name → marketname → brand + model`；`HarmonyVersion`：`software.version → ohos.fullname → os.dist.name + os.dist.version` |
| 日志 | 每条命令原始输出按 Debug 记（截断 1 500 字符），完成时 Info 记耗时与缺失项；全走调用方传入的 `ILogSink` |

### 4.7 `param get` dump 的解析格式（实测）

```
    const.product.model = <MODEL>
    const.product.name = My Phone
    const.product.supportVpn = 1,2,3,4,5,6,7,8
    （条目之间一个空行；4 空格缩进；值里可能含 = 和逗号）
```

`ParseParameters` 用 `^\s*(?<key>[A-Za-z0-9_.\-]+)\s*=\s*(?<value>.*)$`，按行首键名建字典，
值保留原始形态（含逗号与空格），取用方自己 Trim。

## 6. 遗留问题

1. **序列号需 root**：`ohos.boot.sn` 等键返回 `errNum 1002`（无权限），非 root 只能回退成 `ip:port`。
   若要真实 SN，需扩展 `hdc shell` 之外的能力（例如 `hdc file recv` 读特定节点），本机未验证。
2. **SoC 型号需 root**：`/proc/cpuinfo`、`/sys/devices/system/cpu/` 全被拒，`const.chip.platform` 无权限。
   字段当前是「架构 + ABI」，若要芯片型号需另找系统服务或 root。
3. **无线调试端口随机**：实测设备端口是五位数会话端口，`CandidatePorts` 的 8710/5555 打不到它。
   所以**扫描只能自动发现"固定端口"设备和已连接设备**；新设备的随机端口要靠 `KnownEndpoints`
   （上次连过的地址）或用户手填，或 `hdc discover`（前提是放行 UDP 8710 入站）。
4. **`hdc discover` 恒 6.1 s 且恒 `total:0`**：本机防火墙对 8710 没有任何规则。
   需要用户在网络设置里放行 UDP 8710 入站后才可能真正生效——代码已把它放在并行分支，不阻塞主流程。
5. **`tconn` 验证有 0.2 s 级副作用**：会对候选真机建立一次连接再 `-remove`。
   界面上如果同时有别的操作在连同一台设备，可能出现「刚连上又断开」，日志可追溯。
6. **深度扫描默认关闭**：丢包网络下 65 535 端口单机预计 >4 分钟，只在用户明确定位死街时才开。
7. **分辨率是多屏模型**：`hidumper` 输出里 `screen[0]` 之外的屏幕（虚拟屏、折叠副屏）未纳入；
   当前固定取 `physical resolution`，取不到退 `render resolution`，再退 `activeMode`。
8. **Core 日志是中文**：按约定 Core 不出面向界面的文案，日志/注释可以中文；异常消息全部英文，
   界面文案由 App 层资源文件提供。

## 附录：SN 与 SoC 的可得性结论（2026-11-11 真机探测）

对照华为电脑管家多屏协同界面上的字段，逐项复核了我们能读到什么、读不到什么。

### 一、官方 SN 读不到（root 门禁）

| 尝试的命令 | 结果 |
| --- | --- |
| `param get const.product.sn` | `errNum is:106`（参数不存在） |
| `param get const.product.serial` | `errNum is:106` |
| `param get ohos.boot.sn` | `errNum is:1002`（权限不足） |
| `param get persist.sys.serial` | `errNum is:1002` |
| `param get ohos.boot.udid` | `errNum is:1002` |
| `cat /proc/sys/kernel/random/boot_id` | `Permission denied` |
| `hidumper -s MiscDeviceService` | 仅 10 行，无 sn / soc 关键字 |
| `hidumper -ls` | 系统能力列表里没有 DeviceInfoService |

电脑管家能显示形如 `LNG…`（12 位字母数字）的整机 SN，是因为它走的是厂商私有服务通道，普通 shell 拿不到。
**结论：官方 SN 这条字段只能放弃。**

### 二、UDID 可读，但只在本机日志里用，不上界面

`bm get --udid` 的原始输出是两行：

```
udid of current device is :
<64 位十六进制 UDID>
```

注意解析时**不能先压成单行**：第一行里没有十六进制串，压行后正则可能匹配到提示语里的字符。
实现上按行扫描，取第一段 16~64 位十六进制（`HdcDeviceInfoReader.ParseUdid`）。

UDID 属于设备身份标识，**界面不再展示**（原先的「序列号」一行已删除），末尾改为显示「设备地址」= `IP:端口`。

### 三、SoC 型号读不到，用「型号 → 芯片」本地映射表

`const.product.hardware` / `chipset` / `cpu.model` / `soc`、`const.build.soc` / `chip` / `hardware`
全部 `errNum 106`；能读到的只有厂商名（`const.product.manufacturer`）与设备形态（`const.product.devicetype`）。

因此显示逻辑是：

1. 型号命中 `SocByModel` 表 → 显示 `kirin9000s (arm64-v8a)`，与电脑管家一致；
2. 未命中 → 只显示 `aarch64 (arm64-v8a)`，**绝不猜芯片名**。

当前表内条目：`HarmonyOS NEXT 真机（型号略）` / `HarmonyOS NEXT 真机（型号略）` / `HarmonyOS NEXT 真机（型号略）` / `BRA-AL00` → `kirin9000s`；
`MNA-AL00` / `ADY-AL00` / `HBN-AL00` → `kirin9010`。新机型按型号追加即可。

### 四、其余字段的来源

| 界面字段 | 来源命令 |
| --- | --- |
| 名称 / 品牌 / 型号 | `param get const.product.name|brand|model` |
| 鸿蒙版本 | `const.product.software.version`，去掉重复的型号前缀 |
| 内核版本 | `uname -a` 首段 → `HongMeng Kernel 1.13.0` |
| 处理器 | `const.product.cpu.abilist` + 型号映射表 |
| 物理分辨率 | `hidumper -s RenderService -a screen` 的 `physical resolution` |
| 内存 | `cat /proc/meminfo` 的 `MemTotal` |
